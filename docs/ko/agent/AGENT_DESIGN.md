# 에이전트 설계와 검수

[문서 목록](../../README.md) · [호출 가능한 인터페이스](MCP_AUTHORING.md) · [실측](../STATUS.md) · [로드맵](../ROADMAP.md)

이 페이지는 설계상의 선택과 검수 방식만 설명합니다. 공개 API는 인터페이스 문서와 서비스 Schema가 정의하고, 작업 완료율은 실측 기록이 정의합니다. 연구 제안은 출시된 기능으로 취급하지 않습니다.

GUI와 MCP는 같은 애플리케이션 계층 명령을 사용합니다. 각 편집은 캡처한 시작 상태에서 후보를 준비한 뒤 CAS로 히스토리 노드 하나를 커밋합니다. GUI 진입점은 신뢰할 수 있는 사용자 신분으로, MCP는 에이전트 신분으로 호출합니다. 단일 수정은 대부분 프로세스 작업이며, 일괄 처리가 가능한 멤버는 같은 후보를 직접 실행합니다.

작성 포즈는 보조 상태로, 그 자체는 리그 히스토리에 들어가지 않습니다. `preview_set/reset`과 스냅샷 적용은 커밋된 포즈와 잠금을 병합합니다. GUI 포즈, FK/IK 목표와 선택된 모션의 자동 키프레임은 `WorkspacePoseCommands`와 `preview_pose`를 통해 CAS 한 번을 공유합니다. 조회, 수정과 저장은 같은 영속 기준 상태를 읽습니다. 명시적인 무변경은 UI를 바로잡고 재생을 멈출 수 있지만 상태나 히스토리를 진행시키지 않습니다. GUI의 파라미터 수정은 먼저 로컬에 반영되고 FIFO 큐로 커밋됩니다. 큐는 자신이 실제 반영한 커밋만 따라 진행하며 실패하면 커밋된 포즈로 돌아갑니다. 슬라이더를 드래그하는 동안 각 샘플을 작성 포즈에 즉시 기록하고, 놓을 때 한 번만 커밋합니다. 재생과 트래킹은 프로세스 내부 세션입니다([캔버스 렌더러](../spec/CANVAS_RENDERER.md#11-재생과-추적-세션) 참고). 그 프레임 위에 아직 반영되지 않은 수정을 겹쳐 패널, 캔버스, 미리보기와 물리가 같은 포즈를 읽게 합니다.

이미지와 소재가 모델에 들어갈 때 레이어의 식별자를 고정합니다. `layer_import_images`와 GUI 이미지 추가는 전체 묶음을 히스토리 한 번으로 커밋합니다. 소재 레이어 추가, 정합 위치 지정과 확정은 단일 / 원자적 일괄 후보를 공유합니다. 가져온 모델과 직접 만든 부모 디포머 아래의 새 메시는 명시적인 메시 생성 기록을 저장하며, 다시 정합하면 기록을 제자리에서 교체하고 식별자와 부모를 유지합니다. 연속 드래그 배치는 별도의 애플리케이션 세션입니다. 미리보기는 저장에 들어가지 않으며 외부 편집이나 다시 열기로 무효화됩니다.

## 역할 분담

에이전트는 의도를 이해하고, 대상을 고르고, 도구 호출을 계획하고 결과를 관찰합니다. 프로그램은 결정적인 소재, 메시, 파라미터, 물리와 히스토리 작업을 담당합니다. 모델러는 스타일과 최종 효과를 결정합니다.

외부 에이전트는 로컬 MCP를 통해 데스크톱 작업 공간을 조작합니다. 이 문서는 내장 Chat, 범용 자동 머리카락 분할기, 자동 9축 시각 피팅 도구의 존재를 약속하지 않습니다. 이미지 생성은 호스트가 제공하며, 도구는 결과를 받아 배치하고 바인딩합니다.

## 편집 경계

- 오브젝트는 안정적인 ID로 참조합니다. 표시 이름은 식별자를 대신할 수 없습니다.
- 원본 소재, 파생 소재, 메시, 부모, 파라미터와 키폼의 관계를 추적할 수 있어야 합니다.
- 쓰기는 통합 프로젝트 명령과 히스토리를 거칩니다. 렌더링 스냅샷만 수정하면 재구축하거나 다시 열 때 사라집니다.
- `state`는 동시성을 처리하며 작업별 승인이 아닙니다. 잘못된 참조, 부모·자식 순환, 유한하지 않은 수치와 잘못된 토폴로지는 거부해야 합니다. 미술적 효과는 관찰과 진단으로 판단합니다.
- 히스토리는 추가하며 이전 노드를 덮어쓰지 않습니다. 복원 후 편집을 계속하면 분기가 생깁니다. 임시 소재, 일시적인 세션, 커밋된 히스토리와 디스크 프로젝트는 서로 다른 상태입니다.
- 소재 준비, PNG 가져오기, 정합과 재처리는 독립적인 애플리케이션 세션에서 비공개 후보를 준비하고, 보조 CAS로 소재 목록과 불변 파일을 공개합니다. 실제 수정은 영속 state를 진행시키면서 리그 히스토리와 revision을 유지합니다. 네 가지 공개 쓰기는 프로세스 작업이며 취소/충돌 전까지 처리한 일부를 공개하지 않습니다. 커밋 후에는 정확한 결과와 이미지를 유지합니다. 조회와 저장은 캡처한 목록을 사용하고, 구형 v1 프로젝트는 열 때 기존 멤버를 고정합니다.

## 도구 설계

공개 진입점은 관찰, 형상, 키폼, 구조, 소재, 경로, 파라미터, 물리와 히스토리라는 편집 영역을 중심으로 구성합니다. 각 작업은 `domain_operation` 이름과 엄격한 `request` schema를 사용합니다. 애플리케이션 계층 레지스트리가 MCP 공개, 검증과 기능 탐색을 함께 구동하며, 임의의 내부 도구 이름으로 분배하는 기능은 제공하지 않습니다.

`project`는 중립 문서, DTO와 아카이브를 저장합니다. 애플리케이션 계층은 반드시 구현해야 하는 기능 인터페이스, 런타임과 명령 경계를 정의하고, GUI와 MCP는 어댑터를 담당합니다. `WorkspaceBackend`는 호스트가 인터페이스를 조합하는 용도로만 쓰며, 명령 소비자는 필요한 기능에 바인딩하고 예외를 던지거나 빈값을 반환하는 기본 구현을 상속하지 않습니다. PSD/이미지 새 프로젝트와 전환, CMO3 새 프로젝트와 교체는 이미 GUI 없이 동작하는 애플리케이션 계층 가져오기 도구를 공유합니다. GUI는 확인과 화면 투영을 담당하고 MCP는 프로세스 작업을 반환합니다. 작업 공간의 애플리케이션 로직은 UI에 의존하지 않는 `WorkspaceHost` 안에 있으며 `WorkspaceHostPresentation`으로 호스트 UI와 상호작용합니다. 데스크톱 어댑터(`DesktopWorkspace`)는 ViewModel로 이를 구현하고, `psd2live mcp`는 ViewModel을 만들지 않고 `HeadlessPresentation`으로 구현합니다. [헤드리스 호스트](../spec/HEADLESS_HOST.md)를 참고하세요.

로컬 동작은 연속 변형이나 경로로 표현하는 것을 우선하며, 모델이 대량의 정점 위치를 추측하도록 요구하지 않습니다. 연속 작업에서도 좌표, 대상 파라미터 키와 부모 관계를 명확히 해야 합니다. 연속 작업이라고 포즈가 자연스럽거나 토폴로지가 뒤집히지 않는 것은 아닙니다.

원본 이미지 분할은 먼저 `source_get_components`로 현재 메시의 연결 요소를 조회하고, 반환된 순서에 따라 이름을 붙이며 조회 상태를 유지합니다. `source_split_components/source_split_polygon`은 GUI 연결 요소 대화 상자와 독립 애플리케이션 명령을 공유하고, 원자적 일괄 처리와 백그라운드 취소를 지원합니다. `piece_ids`를 지정하면 뒤의 멤버가 새 레이어를 참조할 수 있습니다. 생성된 모델에서는 파츠가 `art_primitive` 기록으로 원래 레이어를 대체하며, 원래 레이어의 기존 키폼, 채널, 블렌드 셰이프, 경로, 정점 가중치와 글루를 가져옵니다. 시뮬레이션 대상, 베이크 오프셋과 연결 역할은 파츠로 옮겨지고 관련 없는 오브젝트의 편집은 영향을 받지 않습니다. 가져온 CMO3 모델은 기존 기록을 사용하며 원래 레이어를 소프트 삭제합니다. 일반, 분할, 새로 만든 메시와 가져온 CMO3 메시는 레이어별/전역 메시 업데이트 및 초기화 시 순서가 있는 메시 교체를 저장하고, 바인딩과 베이크 오프셋을 옮기며 초기 로그 기준 상태를 유지합니다. 매번 이전 토폴로지를 보간해 교체하므로, 설정을 초기화해도 토폴로지가 거칠어질 때 잃어버린 세부는 복원되지 않습니다. 분할은 기존 픽셀만 배분하며 가려진 부분을 그려 넣는 작업을 대신하지 않습니다.

앞뒤 가림 제작은 `source_split_depth`를 사용합니다. 원래 메시 ID로 원본과 중간 오브젝트를 지정하고 뒤 레이어와 앞 레이어라는 두 새 레이어로 원본 메시를 대체합니다(가져온 CMO3 모델은 원본 메시 위에 앞 레이어를 복제). 방향성 글루가 앞 레이어를 뒤 레이어에 따라가게 하고 두 레이어의 그리기 순서를 고정합니다. 앞뒤 레이어, 메시와 글루 ID를 미리 지정해 같은 원자적 일괄 처리에서 페인팅이나 키폼 작성을 이어갈 수 있으며, 작업의 최종 상태는 새 레이어 ID를 제공합니다. GUI와 애플리케이션 후보를 공유하고 기존 바인딩을 지원하며, 입 파츠는 선택한 메시만 복제합니다. 가져온 CMO3 모델도 지원하고 GUI의 앞뒤 레이어 진입점도 같은 동작을 합니다. 앞 레이어 페인팅은 토폴로지를 보존하며 명시적인 메시 설정으로는 재생성할 수 있습니다. 숨겨진 내용은 별도로 그려 넣어야 합니다.

즉시 호출과 백그라운드 작업은 같은 애플리케이션 계층 구조화 오류를 사용합니다. 에이전트는 오류 코드와 충돌 맥락에 따라 복구 동작을 고르며, 수정 후 새 시도는 새 요청 ID를 사용합니다. 작업 조회 성공이 작업 자체의 성공을 뜻하지는 않으므로 반드시 작업 상태를 읽어야 합니다.

모든 공개 작업은 출력 계약을 선언해야 합니다. 결과는 레지스트리에서 중복을 제거한 뒤 내부 검증되며 같은 완전한 MCP outputSchema가 공개됩니다. 백그라운드 작업은 최종 업무 상태 schema도 공개해야 합니다. 상태 분기는 어떤 필드가 존재하는지 명확히 하며 성공 결과와 실패 오류를 섞을 수 없습니다. 기능 탐색 자체는 로컬 재귀 정의로 중첩 schema를 검증하고, 최종 상태 계약은 백그라운드 기능에만 존재합니다. 복합 inspect에는 scope 판별 필드가 있고, 소재와 시뮬레이션 출력은 가공, 정합, 방향과 품질 진단을 보존합니다. `output_contract`는 서비스 구현 문제를 뜻하며 롤백의 증거로 삼을 수 없습니다.

조회는 먼저 요약을 반환하고 대상과 페이지에 따라 확장합니다. 복합 작업 공간, 뼈대와 모션 조회는 런타임의 동일한 불변 캡처를 사용하며 반환되는 영속 상태에 동시 버전을 섞지 않습니다. 미리보기 조회는 커밋된 포즈/잠금을 읽으며 평가 프레임이나 커밋되지 않은 UI 값으로 대체하지 않습니다. 이미지에서는 캔버스 카메라를 고정하고 관련 영역과 포즈 수를 제한합니다. 원본 소재, 합성 미리보기와 실제 런타임 모델을 명확히 구분합니다.

## 한 작업의 검수

1. **기준 상태**: HEAD, 대상 오브젝트, 파라미터와 예상 변화를 기록하고 관련 부위와 전체 이미지를 확보합니다.
2. **소재**: 투명 가장자리, 방향, 캔버스 위치와 가림 여유를 확인합니다. 기존 픽셀의 분할은 숨겨진 내용을 완성하는 것과 다릅니다.
3. **구조**: 부모, 마스크, 그리기 순서, 직접 바인딩과 상속 파라미터를 확인합니다. 독립 움직임이 필요할 때만 디포머를 추가합니다.
4. **형상**: 중립 포즈, 끝점, 필요한 조합 각도와 중간값을 확인합니다. 수정 전후를 비교해 관련 파츠가 손상되지 않았는지 확인합니다.
5. **물리**: 먼저 출력 파라미터에 움직임 형상을 만든 뒤 구동을 설정합니다. 시간 샘플링으로 지연, 복원과 안정 상태를 관찰합니다.
6. **영속화와 전달**: 저장하고 복원한 뒤 다시 내보냅니다. 보고서와 대상 소프트웨어에서의 실제 효과를 확인합니다.

기하가 유효하다는 것은 프로젝트를 계산할 수 있다는 뜻일 뿐, 4–6번을 대신하지 않습니다. 참고 이미지 생성도 실제 모델의 움직임을 대신할 수 없습니다.

## 비용과 중단 조건

기존 ID, 공간 매핑과 성공 응답의 `state`를 재사용하고 매번 전체 스캔하지 않습니다. 정적 비교는 작은 이미지 묶음으로 합치고, 의심 지점을 찾을 때만 부분 이미지를 확대합니다. 먼저 레이어 순서, 위치, 바인딩과 픽셀 문제를 구분한 뒤 이미지 재생성 여부를 결정합니다.

시간, token / 이미지 사용량과 재작업 횟수를 기록합니다. 사용자 예산에 도달했거나, 필요한 외부 입력을 얻을 수 없거나, 수정을 계속해도 유효한 진전이 없다면 구체적인 장애물과 기존 성과를 보고해야 합니다. 반복 호출을 성공의 증거로 삼지 않습니다.

## 후속 설계 방향

이번 구조는 독립 애플리케이션 계층, 단일 원자적 일괄 처리, 프로세스 내부 백그라운드 작업과 전체 GUI 업무 기능을 채택하며, 호출 간 트랜잭션, 내장 채팅이나 독립 헤드리스 서버는 제공하지 않습니다. 일괄 재구축, 가져오기, 저장과 내보내기 작업은 이미 연결이 끊겨도 계속 실행하고 재시도를 중복 제거합니다. GUI 업무 진입점은 모두 공유 명령에 연결되어 있습니다(공개 작업 190개, 백그라운드 72개, 일괄 멤버 87개). 데스크톱 창 검수, Cubism SDK를 포함한 실행 등 미완료 항목과 더 넓은 제품 방향은 [로드맵](../ROADMAP.md)에서 관리합니다. 리팩터링 중의 단계 기록은 보관되었으며 더 이상 저장소에 커밋하지 않습니다.
