# PSD 가져오기 응답성

PR #47의 후속 작업입니다. 그 PR은 시작 프리셋 중 대기열에 쌓인 메시 분할 요청을 수정합니다. 거기서 보고된 2520² PSD 한 개에서의 약 220 ms 멈춤은 관찰 결과일 뿐, 대용량 파일에 대한 성능 보장이 아닙니다.

## 첫 번째 변경: 비공개로 준비하고 한 번에 게시

데스크톱 경로는 `analyze` → `startWorkspaceImport` → `WorkspaceHost.importPsd` → `WorkspaceSourceImporter`입니다.

| 단계 | 실행 / 변경 |
| --- | --- |
| 소유한 PSD 캡처, 읽기와 디코딩 | 기존 IO 워커 경로. 이제 따로 시간을 잽니다. |
| 연결된 소재 구성, 원본 래스터 해시 | 단일 Default 워커 작업으로 옮겼습니다. 원래 픽셀 배열, 해시 알고리즘, 소재 순서와 연결은 유지됩니다. 항목 사이마다 취소를 확인합니다. |
| 미리보기 구성 | 기존 백그라운드 미리보기 빌더. 가져오기에서 그 경과 시간도 기록합니다. |
| 리비전 계산, 초기 히스토리 검증과 준비 | Default 워커로 옮겼습니다. 검증된 설치 후보는 실행 중인 런타임에 부작용을 주지 않습니다. |
| UI 투영과 런타임 게시 | 준비가 끝난 뒤 호출자 스레드에서 동기적으로 실행되는 것은 그대로입니다. 예상 런타임 상태와 저장하지 않은 변경 보호를 다시 확인합니다. 이 단계 전에 취소를 확인합니다. |
| 렌더러에 알림 | 원래 경로 그대로이며 따로 시간을 잽니다. 알림 시간은 비동기 GPU 업로드나 첫 프레임 지연을 측정하지 않습니다. |

모델을 부분적으로 게시하거나 레이어별로 병렬 처리하지 않습니다. 기존 시작 프리셋과 메시 분할 대기열 규칙은 바뀌지 않습니다. 다른 동기식 런타임 설치 호출자는 기존 동작을 유지합니다.

## 측정 재현

JDK 21과 저장소의 Gradle 의존성이 필요합니다. 저장소 루트에서 실행합니다.

```sh
./gradlew test --tests '*WorkspaceSourceImporterTest' --tests '*WorkspaceInstallationTest' --tests '*WorkspaceRuntimeConcurrencyTest' --tests '*MeshSplitMenuScenario' -Ppsd2live.testForks=1

PSD2LIVE_IMPORT_PROFILE=1 PSD2LIVE_SPLIT_SCALE=6 ./gradlew test --tests '*MeshSplitMenuScenario' --rerun-tasks --info -Ppsd2live.testForks=1
```

배율 6은 합성 420² 픽스처를 2520²로 만듭니다. 환경 변수는 테스트 JVM까지 전달되며, 기존 `psd2live.scenario.splitScale` 시스템 속성도 그 JVM에 설정되어 있으면 인식됩니다. `PSD2LIVE_IMPORT_PROFILE=1`은 이 시나리오에서 기존의 옵트인 `RigBuildProfile` 기록기를 켭니다. 단계별 합계, 호출 수, 실행 스레드 이름을 출력합니다. `raster: SHA-256`은 가져오기 밖의 해시를 포함한 캐시 미스를 측정합니다. 단계 합계는 중첩되어 있으므로 서로 더하면 안 됩니다. 미리보기 구성 경과 시간 단계는 일시 중단을 포함하며, 한 스레드에서 실행된다고 주장하지 않습니다.

시나리오는 10 ms마다 예약된 Main 스레드 틱 사이의 최대 간격을 보고합니다. 이제 측정 동작을 시작하기 전에 티커가 시작될 때까지 기다립니다. 이는 스케줄링 간격의 관찰이지 UI 전용 CPU 시간의 정밀한 측정이 아니며, 기기에 따라 달라지는 통과/실패 한도도 없습니다. 가져오기 간격에는 겹치는 시작 프리셋 작업이 포함될 수 있으니, 단계별 시간으로 그 작업을 분리하세요.

실제 PSD는 같은 데스크톱 가져오기 경로를 JFR이나 샘플링 프로파일러로 프로파일링하고 다음을 기록합니다.

- 빌드 SHA, OS, JDK, CPU, 힙, 파일 바이트 수, 캔버스 크기, 레이어 수, 래스터 총 바이트 수.
- 가져오기와 프리셋 시간을 나눈 값, 최대 UI 스케줄링 간격, 처음 사용 가능한 미리보기, 총 시간, 최대 메모리/GC.
- 콜드 프로세스 1회 실행과 반복된 웜 실행. 표본 하나가 아니라 중앙값과 꼬리 동작을 보고합니다.
- 2520² 기준선, 더 큰 실제 제작 PSD, 캔버스 크기는 비슷하지만 레이어 수/래스터 총량이 다른 파일.

이 변경만으로는 전후 속도 향상이나 절대적인 응답성 한도가 확립되지 않았습니다.

## 커버리지와 남은 작업

| 커버리지 | 상태 |
| --- | --- |
| 시작 페이지 가져오기 → 스캔 → 분할 → 다시 스캔 | #47의 기존 `MeshSplitMenuScenario`. |
| 소재/리비전 소스 순회는 호출자 밖에서, 투영은 호출자로 돌아와서 실행. 원래 래스터 공유와 정규 리비전이 일치 | `WorkspaceSourceImporterTest` 추가. 주입한 리더/빌더는 PSD 디코더의 정확성이 아니라 조율을 분리해 검증합니다. |
| 리비전 준비 중 취소하면 아무것도 게시하지 않음 | 게이트 기반의 결정적 가져오기 테스트 추가. |
| 동시 편집이 준비된 설치를 거부, 준비 과정이 런타임 잠금을 점유하지 않음 | `WorkspaceInstallationTest` 추가. |
| 변경 상태 가드, 투영 실패, 히스토리 불일치 거부 | 준비된 설치 테스트 추가. |
| 대용량 실제 PSD 성능, 렌더러/첫 프레임 지연, 메모리 회귀 | 대표적인 하드웨어에서의 측정이 아직 필요합니다. |

여기서 추가한 테스트는 의존성이 갖추어진 환경에서 실행해야 합니다. 테스트가 있다는 사실을 통과 결과로 해석하지 마세요.

측정 후 다음 단계:

1. 동기식 투영이 계속 주된 비용이라면, 반복되는 상태 파생을 줄이고 진행 상황 업데이트를 제한합니다. 모델/문서 게시가 한 번에 일관되게 이루어지는 것은 유지합니다.
2. 렌더러 설치가 주된 비용이라면, SDK/GL 스레드 소유권을 확인하고 CPU 준비 작업만 워커로 옮기며, 원자적 전환 전에 비공개 교체 세션에서 크기를 제한한 업로드 배치를 고려합니다. 배치를 활성화하기 전에 취소/실패 시 리소스 정리 테스트를 추가합니다.
3. 취소/다시 가져오기, 프로젝트 닫기/전환, 가져오기 실패, 결정적으로 게이트된 프리셋/분할 겹침에 대한 데스크톱 수준 회귀 커버리지를 확장합니다. 초기 런타임 상태 토큰이 이미 오래된 준비 가져오기를 거부하지만, 이러한 UI 시퀀스는 아직 명시적인 커버리지가 필요합니다.
