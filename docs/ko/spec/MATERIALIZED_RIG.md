# 실체화된 리그: 작성 리그를 기준 데이터로 삼는 프로젝트 모델

[문서 목차](../../README.md) · [문서 계층](DOCUMENT_LAYER.md) · [프로젝트 형식](PROJECT_FORMAT.md)

> 상태: 0–5단계가 모두 구현되었습니다. 분할과 생성 설정, 분류의 병합, “생성 업데이트”와 재생성 시험 실행도 포함됩니다(설계와의 차이를 나열한 [구현 진행 상황](#10-구현-진행-상황) 참고). 이 페이지는 목표 모델, 저장, 작업 분류, 재생성 병합 규칙, 단계별 계획을 다룹니다. 구현된 부분의 사실은 [문서 계층](DOCUMENT_LAYER.md)과 [프로젝트 형식](PROJECT_FORMAT.md)을 기준으로 합니다.

## 1. 배경

### 1.1 현황

`PuppetModel`은 저장하지 않습니다. 열기, 실행 취소, 히스토리 전환, 편집 커밋 때마다 다음을 수행합니다.

1. `RigBuilder`가 **현재 코드**와 **현재 설정**에 따라 원본 이미지로부터 기반 리그를 생성합니다(뼈대 베이크, v2 분할 파츠의 주차 포함).
2. `RigEditOverlay.applyTo`가 그 위에 레거시 형식의 정적 편집과 `authoringJournal`을 차례로 재생합니다.
3. 흔들림, 시뮬레이션 반영, `skeleton.skin`, 생성 결과 재정의가 `DocumentGenerators`의 그래프에 따라 실행되고, 이어서 물리와 모션을 다시 생성합니다.

저널 항목은 생성된 디포머, 파라미터, 메시를 ID로 참조하며, 일부 항목(`vertex_group_put`, `canvas_geometry`, `set`의 정점 오프셋, 경로, Glue 정점 쌍, 분할 기록)은 **정점 인덱스**로도 참조합니다. 항목은 그것이 기록된 바로 그 순간, 그 기반 리그 위에서만 확실히 성립합니다. 이후 기반 리그의 구조가 바뀌면 대상을 찾지 못하거나, 엉뚱한 객체에 조용히 적용될 수 있습니다.

### 1.2 구조 드리프트의 원인

| 원인 | 예 |
| --- | --- |
| 생성 설정 | 머리카락 시뮬레이션을 켜면 `DeformHair*Physics`와 `ParamHair*`가 삭제됨. 뼈대를 켜면 팔 늘어뜨림 Warp와 좌우 쌍 Warp가 더 이상 생성되지 않음. `runtimeTarget`에 따라 뼈와 시뮬레이션 파라미터가 키폼 축과 블렌드 폼 사이를 오감 |
| 뼈대 | 바인딩된 메시가 뼈 회전 아래로 재부착됨, 관절 행 삽입(정점 수 변화), 메시 없는 연결 뼈 접기 |
| 분할과 원본 이미지 | 파츠가 원래 메시를 대체함. 새 파츠가 프레임 생성에 참여해 다른 객체의 프레임을 바꿈 |
| 생성 코드 자체 | 생성 규칙, 기본 메시, ID 파생의 어떤 수정이든 이전 프로젝트의 기반 리그를 바꿈 |

### 1.3 재생을 지키기 위해 이미 치른 대가

기존 보호 장치는 각각 일부 경우만 다룹니다.

- 생성 입력 고정: `generationSource`, `meshSource`, `mesh_generation_baseline`(메시 설정)
- 생성 마이그레이션: `RigGenerationMigration`이 설정/분류가 바뀔 때 마이그레이션을 저널 레코드 `rig_generation_transition`(생성 리그 전체의 JSON을 포함)으로 기록하고, 폐기된 객체를 유지
- 더 이상 생성되지 않는 부모: `VanishedParent`, `ArtPrimitiveJournal.rehome`, 구조 편집 `bind`/`move`의 건너뛰기
- 분할: v1/v2 두 종류의 `art_primitive` 레코드, v2의 승객, 주차(`PrimitiveSkins`), 2회 캡처, 승객 허용 오차(`StubTolerance` / `SupersededEntryNote`), 뼈대 베이크 전 파츠 디코딩(`skinnable`)
- 뼈대: `SkeletonCanvasSkin.lockedTopology`, `handEditedTopology` 토폴로지 잠금, 저널이 배치한 메시의 사후 스키닝
- 성능: `ReplayCheckpoints`, `GeneratorReuse`, 단계 캐시와 헤드 캐시. 모두 매 재생을 충분히 빠르게 하기 위한 것

최근의 같은 유형 수정(2026-10-07 ~ 10-08): `7f30f7aa`(머리카락 시뮬레이션이 Warp를 삭제한 뒤 v2 파츠의 부모가 없어짐), `2d6d0b7d`(뼈대를 켠 뒤 팔 늘어뜨림 Warp가 사라짐), `36d6fbb5`(저널이 뼈대 베이크가 읽는 내용을 바꾸면 캐시된 기반에서 이어서 재생할 수 없음), `5019b69b`(뼈에 바인딩된 메시가 저널에 의해 재부착됨), `29099a3a`(파츠가 뼈대 베이크 이후에야 나타남), `220c7d5a`(프리셋이 기반을 다시 빌드할 때 파츠가 일반 레이어로 생성됨), `ea226c07`(v1 파츠가 직전 생성에 없음), `a08df353`(v2 파츠의 부모 체인 편집이 두 번 적용됨), `3c36db5a`(생성 입력 고정 전에 추가된 레이어가 조용히 다시 생성됨).

### 1.4 아직 다루지 못한 공백

“생성 설정이 구조를 바꾸는데 저널에 이미 참조가 있는” 경우를 점검한 결과입니다.

| 트리거 | 무효가 되는 항목 | 기존 보호 |
| --- | --- | --- |
| 머리카락 시뮬레이션 켜기/끄기 | `ParamHair*`를 키로 하거나 `DeformHair*Physics`를 대상으로 하는 `set`, `canvas_geometry`, 이름 변경, 패널 편집, 그 아래에 새로 만든 Warp가 오류. 그 Warp 위의 `set`은 조용히 건너뜀 | `bind`/`move`와 분할 파츠 재부착뿐. `RigGenerationMigration.settingsChanged`에 이 두 스위치가 없음 |
| 기존 흔들림 복원, 시뮬레이션 삭제 | 시뮬레이션 출력 파라미터를 키로 하는 항목이 오류 | 없음 |
| 뼈대 켜기, 뼈 추가·삭제 | 사라진 쌍 Warp와 뼈 위의 항목이 오류. 관절 행 때문에 `vertex_group_put`, `set` 오프셋, `canvas_geometry`, `path_put`의 정점 수가 맞지 않음. Warp 아래에서 기록한 정규화 오프셋이 뼈 공간으로 바뀐 뒤 조용히 어긋남 | 토폴로지 잠금은 `canvas_topology`와 저널이 배치한 메시만 봄. 정점 그룹이 있는 일반 바인딩 메시는 잠그지 않음 |
| `runtimeTarget` | `set`이 조용히 블렌드 폼 경로로 바뀜. 블렌드 폼 파라미터 위의 Glue 키폼이 오류 | 없음 |

위의 허용 오차 경로를 제외하면, 재생이 하나라도 실패하면 전체 재빌드가 실패하며 오류는 메시지 하나뿐입니다. 커밋이 거부되고, 프로젝트를 열거나 히스토리를 전환할 때 모델을 얻지 못합니다.

### 1.5 원래 설계와의 차이

프로젝트 형식의 원래 설계는 “문서 계층은 선언적 상태만 저장하고, 프로젝트를 열 때 더 이상 명령 재생으로 모델을 재빌드하지 않는다. 명령 히스토리는 유지하되 실행 취소와 분기에만 쓴다”를 요구했고, v1 마이그레이션 때 “현재 버전으로 한 번 재생해 결과를 실체화해 저장한다”고 했습니다. 이미 구현된 부분은 내용 해시, 생성기 의존성 그래프, 생성 캐시, 3방향 병합, 내용 주소 방식의 v2 아카이브입니다. 재정의와 3방향 병합은 흔들림, 시뮬레이션, `skeleton.skin`에만 연결되어 있었습니다. 이 문서를 시작할 때 구현되지 않은 것은 핵심 한 단계였습니다. v2 노드가 저장하는 것은 여전히 “원본 이미지 + 설정 + 저널”이었고, 기반 리그는 매번 현재 코드로 다시 생성되었습니다. 이 단계는 이제 이 문서에 따라 구현되었습니다([구현 진행 상황](#10-구현-진행-상황)).

## 2. 목표와 비목표

**목표**

- 열기, 실행 취소, 히스토리 전환은 리비전이 저장한 실체화된 리그에서 바로 모델을 얻습니다. 생성 코드나 생성 설정이 바뀌어도 이미 저장된 리비전을 여는 데 영향이 없습니다.
- 편집 명령은 커밋 시 현재 모델에 한 번 실행되고, 결과는 리비전과 함께 저장됩니다. 명령은 실행 시점의 모델 위에서만 성립하면 됩니다.
- 생성 입력을 바꾸는 것은 명시적인 재생성 트랜잭션입니다. 다시 생성한 뒤 사용자의 수정을 병합하며, 병합할 수 없는 경우는 구조화된 문제로 보고하고 커밋 전에 미리 볼 수 있습니다. 열 때 무너지는 대신입니다.
- 생성기의 개선은 더 이상 이전 프로젝트를 자동으로 다시 쓰지 않습니다. 사용자가 “생성 업데이트”를 시작합니다.

**비목표**

- 명령을 없애지 않습니다. GUI와 MCP는 여전히 같은 JSON 명령과 원자적 일괄 처리를 공유하며, 커밋 경계(후보 → CAS → 히스토리 노드 하나)는 바뀌지 않습니다.
- 모든 편집을 “생성 결과 + 재정의”로 다시 쓰지 않습니다. 평가할 때마다 다시 실행되는 모디파이어(흔들림, 시뮬레이션 반영, `skeleton.skin`)만 재정의를 사용합니다.
- 미리보기 런타임 패키지, 아틀라스 페이지, 물리와 모션의 생성 결과는 저장하지 않습니다.

## 3. 모델

```
문서 입력 ──(재생성 트랜잭션)──▶ G 생성 스냅샷 ──┐
                                                 ├─ 3방향 병합 ─▶ M 실체화된 리그 ──▶ 모디파이어 ──▶ 미리보기 / 내보내기
편집 명령 ───────────(직접 적용)─────────────────┘
```

| 객체 | 내용 | 현재 대응물 |
| --- | --- | --- |
| **M 실체화된 리그** | 작성 리그: 기반 생성(뼈대 베이크 포함)에 모든 편집을 더한 것으로, 흔들림, 시뮬레이션 반영, 재정의 병합 전. 텍스처 좌표는 캔버스 단위(아틀라스에 바인딩되지 않음) | `RigEditOverlay.authored(BuiltRig)`의 결과 |
| **G 생성 스냅샷** | 직전 재생성 때 생성기의 출력으로, 편집되지 않은 것. 재생성 병합의 공통 조상으로만 씀 | `BuiltRig.resolvedPuppet()`(승객 제거, 파츠 배치)의 바인딩되지 않은 형태 |
| **생성 메타데이터** | 메시 → 원본 레이어 매핑, 파츠 슬롯과 중립 경계, 얼굴 중심과 반지름, 생성기 버전, 생성 입력 요약 | `BuiltRig`에서 `puppet` 이외의 필드 |
| **모디파이어** | `skeleton.skin`, 흔들림, 시뮬레이션 반영, 생성 결과 재정의 병합, 물리 그룹, 생성 모션 | `DocumentGenerators`에서 저널 뒤의 노드 |

- **열기**: M과 메타데이터 읽기 → 원본 이미지 분석(분류. 인터페이스와 프리셋용) → 아틀라스 패킹과 바인딩 → 모디파이어 실행 → 미리보기 컴파일.
- **G는 재생성할 때만 읽으며**, 열 때는 디코딩하지 않습니다.

## 4. 작업 분류

| 분류 | 작업 | 처리 |
| --- | --- | --- |
| A 직접 편집 | `canvas_geometry`, `canvas_topology`, `canvas_create_warp/rotation`, Glue 생성과 편집, `path_put/delete`, `vertex_group_put/delete`, 키폼 `set/copy/delete`, `parameter_keys`, `structure`(파라미터 추가·삭제·변경, 바인딩, 이동, 이름 변경 포함), `warp`, `canvas_mesh_create`, 메시 표시 여부와 재질 | 명령이 기존 `apply` 의미(엄격함. 없는 대상을 건너뛰지 않음)대로 M에 적용됨. G는 그대로 |
| B 재생성 트랜잭션 | 메시 설정, 입 모양 등 생성 설정, 머리·몸 강도와 `rigTuning`, 분류와 부모 재정의, 레이어 추가·삭제와 복원, 분할, 메시 재빌드가 필요한 페인팅과 이미지 교체, 캔버스 사각형 이동, 뼈대 정의, 머리카락 시뮬레이션 켜기/끄기, `runtimeTarget`, 생성기 버전 업데이트 | G′를 다시 생성하고 5장에 따라 M′를 병합해 (G′, M′)를 얻음 |
| C 모디파이어 설정 | 흔들림, 시뮬레이션(베이크 결과 포함), 물리 그룹과 순서, 프레임 레이트, 생성 모션과 클립 | 문서의 모디파이어 설정만 바꿈. M, G는 그대로 |
| D 바인딩과 내보내기 | 텍스처 밀도, 예산, 고정 위치, 아틀라스 배치, 메시를 재빌드하지 않는 페인팅과 이미지 교체, 내보내기 설정 | 아틀라스 바인딩이나 내보내기에만 영향. M, G는 그대로 |

- A 분류의 후보는 “M 위에서 명령 실행 + 모디파이어 실행”입니다. 캔버스 드래그 미리보기도 M 위에 커밋 대기 중인 명령을 적용합니다.
- B 분류는 잠금 밖에서 계산하며, 진행 상황을 보고하고 원래 코루틴의 취소를 확인합니다. 커밋 규칙은 기존 재빌드형 커밋과 같습니다.
- 히스토리 노드는 실행한 명령을 저장하며, 표시, 감사, MCP에 쓰고 더 이상 재빌드에는 쓰지 않습니다.

### 4.1 기록 계층과 적용 계층

A 분류 명령은 사용자가 보는 완성 상태 리그(M + 모디파이어) 위에서 기록되고, M(모디파이어 이전)에 적용됩니다. 모디파이어가 추가한 파라미터와 축(시뮬레이션 모드 파라미터, 흔들림 파라미터, 대상 위의 그 키폼 축)은 M에 존재하지 않으므로, 저널에 쓰기 전에 명령을 M 기준으로 정규화합니다.

- 키폼 좌표 중 모디파이어가 추가한 축(대상이 완성 상태에는 가지지만 M에는 없는 축)은 기본값이면 제거하며, 명령은 모디파이어가 생성의 근거로 삼는 정지 칸에 떨어집니다. 기본값이 아닌 모디파이어 칸은 생성 결과 재정의 레코드(`generated_override`)가 모디파이어 뒤에서 적용합니다.
- 관찰 포즈는 대상 기하가 실제로 읽는 파라미터(대상 자신의 키폼 축, 블렌드 폼 파라미터와 그 제한 파라미터, 키폼 좌표 안의 파라미터)만, 그것도 기본값이 아닌 것만 남깁니다. 기하 편집은 Cubism과 마찬가지로 부모 로컬 공간에서 대상의 키폼에 작용합니다. 대상 자신의 파라미터만 키 위에 있으면 되며(편집 전에 가장 가까운 키로 스냅), 부모 파라미터는 어떤 값에 있어도 됩니다. 부모를 통해서만 대상을 움직이는 모디파이어 파라미터(예: 상위 Warp에 걸린 흔들림)는 그때 어떤 값이든 기록에 들어가지 않습니다(`RigGeometryTools.referencePose`. 컴파일 시 `canvas_geometry`와 Bezier 레코드에 일괄 적용).
- **모디파이어 파라미터의 입양**: 명령이 모디파이어의 파라미터를 참조하면(다른 객체에 키를 찍기, 채널 키폼, 이름 변경, 범위 변경) 그 앞에 모디파이어의 현재 정의대로 그 파라미터를 만드는 `structure` 레코드(`GeneratedParameterAdoption`)를 씁니다. 이후 파라미터는 문서에 속합니다. 저널이 참조할 수 있고, 모디파이어는 이미 있는 파라미터를 그대로 사용하며(기존 파라미터를 다루는 것과 같음), 모디파이어를 삭제해도 파라미터와 사용자가 그 위에 만든 키폼은 남습니다. 이는 Cubism에서 물리 출력 파라미터가 일반 파라미터인 것과 일치합니다. 모디파이어 자신의 파라미터는 모디파이어와 함께만 삭제할 수 있습니다. 입양된 파라미터는 삭제할 수 있으며, 모디파이어가 자기 정의대로 다시 만듭니다.
- **모디파이어가 소유한 키폼**: Bezier 편집과 키폼 `set`(MCP `rig_deform` 포함)이 모디파이어 칸에 쓰면 생성 결과 재정의로 바꿔 씁니다. 자식 위치를 유지하는 편집, 모디파이어 칸으로의 복사나 모디파이어 칸에서의 복사, 모디파이어 축 위의 키 추가·삭제는 재정의로 표현할 수 없으므로 기록 시 거부하고 수정해야 할 모디파이어를 알려 줍니다(`GeneratedOverrides.ownedWrites`).
- Glue는 Cubism과 마찬가지로 정지 형태(기본 포즈)에서 쌍을 맺습니다. 컴파일 시 레코드에서 포즈를 제거하며, 용접은 두 메시의 정지 기하에만 의존하고 모디파이어와 무관합니다. 캔버스는 붙이기 전에 파라미터를 기본값으로 되돌립니다. 이전에 기록된 포즈 포함 레코드는 원래 포즈대로 재생합니다.
- 판단 근거는 두 리그 자체입니다. 모디파이어 파라미터는 완성 상태에는 있고 M에는 없는 파라미터이고, 모디파이어 축은 대상이 완성 상태에는 가지지만 M에는 없는 축이며, 키폼의 소유자는 모디파이어 그래프에서 가져옵니다. 위의 정규화는 `JournalRecording.record`에 모여 있으며, 저널에 쓰는 모든 편집이 이를 거칩니다.
- 세션 중의 후보는 M 위에서 새 명령을 실행한 뒤 모디파이어를 실행하며, 열 때의 빌드와 같은 경로입니다. M에 적용할 수 없는 명령은 편집 시점에 바로 실패하며, 프로젝트에 쓰인 뒤 다시 열 때가 되어서야 오류가 나지 않습니다.

## 5. 재생성 병합

입력: 공통 조상 G, 새로 생성한 G′, 현재 M. 출력: M′와 문제 목록. 객체는 안정적인 ID로 맞춥니다(파라미터, 파츠, 디포머, 메시, ID가 있는 Glue, 경로. 정점 그룹은 “메시 + 이름”, ID가 없는 Glue는 메시 쌍으로). “사용자가 바꿨는지”는 항상 M과 G의 비트 동등성으로 판단합니다. M과 G는 모두 저장된 값이므로 재계산에서 오는 부동소수점 오차가 없습니다.

| 경우 | 규칙 | 보고 |
| --- | --- | --- |
| M에만 있음(사용자가 만듦) | 유지. 부모의 내용을 생성기가 다른 디포머로 넘긴 경우([승계](#113-승계)) 그에 따라 재부착. 그렇지 않고 부모가 M′에 없으면 G에서의 조상 체인을 따라 G′에 아직 있는 가장 가까운 조상으로 재부착. 기본 포즈에서의 캔버스 위치는 그대로이며, 키폼 오프셋은 부모 공간의 선형 부분으로 환산 | `followed` / `rehomed` |
| G에 있고 G′에 없음 | M의 그 객체가 G와 같으면 삭제. 다르면 폐기된 객체로 유지 | `retired_kept` |
| G에 있고 M에 없음(사용자가 삭제) | G′가 여전히 생성해도 삭제 상태 유지 | — |
| G′에 새로 추가됨 | 추가 | — |
| 셋 모두에 있음: 필드 | 필드별 3방향 병합. 사용자가 바꾸지 않은 것은 G′를 따르고, 생성이 바뀌지 않은 것은 사용자 값을 유지하며, 양쪽 다 바뀌면 사용자 값을 유지 | `conflict` |
| 셋 모두에 있음: 부모 | 사용자는 부모를 바꾸지 않았고 G′는 바꿨으면 G′를 따르며, 캔버스 위치가 바뀌지 않도록 로컬 좌표와 키폼을 환산. 사용자가 재부착한 부모가 승계되면 그에 따라 재부착 | `reparented` / `followed` |
| 셋 모두에 있음: 키폼 | 축은 합집합. 칸별, 정점(또는 제어점)별 3방향 병합 | `conflict` |
| 토폴로지가 다름(G와 G′) | 사용자 차이 M − G를 캔버스 텍스처 좌표 마이그레이션(`RasterMeshJournal.prepare`의 정점 출처)으로 G′의 토폴로지에 옮겨 다시 더함. 정점 그룹, 경로, Glue 정점 쌍도 같은 마이그레이션 계획으로 이동(`MaterializedMeshRebuild`를 그대로 사용) | `topology_migrated` |
| 사용자가 토폴로지를 바꿈(M과 G의 토폴로지가 다름) | 사용자 토폴로지 유지. G에 대한 G′의 생성 변화를 캔버스 텍스처 좌표로 사용자 정점에 매핑: G′의 부모를 취하고, 정지 위치는 M이 표시하는 위치에 G에 대한 G′의 캔버스상 이동을 더한 것, 키폼과 블렌드 폼은 G′의 것(사용자 정점에 샘플링)에 G에 대한 사용자 차이(새 부모로 환산)를 더한 것. 메시를 매칭할 수 없거나 새 부모가 수용할 수 없으면 M을 통째로 유지 | `topology_followed` / `topology_kept` |
| G′가 파라미터를 삭제했지만 M에 참조가 있음 | 파라미터를 폐기된 파라미터로 그 위의 사용자 키폼과 함께 유지 | `retired_kept` |

- 문제는 구조화된 레코드로 보고합니다(`RigRegeneration.Issue`: 종류, 객체, 설명). 등급은 `core/quality/RegenerationRule`만이 정합니다. 충돌, 사용자 토폴로지 유지, 객체 버림은 warning이고, 재부착, 승계에 따른 재부착, 폐기된 객체 유지, 부모 변경, 토폴로지 마이그레이션, 생성을 따른 사용자 토폴로지는 info입니다. 병합은 체크포인트를 쓸 때 이미 끝났으므로 보고는 관찰용이며(`RegenerationQuality`, `can_proceed`는 항상 true) 커밋을 막지 않습니다. 마지막 체크포인트의 문제가 `workspace_inspect`의 `quality.regeneration`에 들어갑니다.
- B 분류 작업의 시험 실행: `workspace_preview_regeneration`(MCP)과 “모델 → 생성 결과 업데이트 미리 보기”(GUI)는 쓰게 될 체크포인트와 그 병합 문제를 반환하며 커밋하지 않습니다.
- 설계는 `format-compile`의 `ThreeWayMerge`(MIT)를 재사용할 계획이었습니다. 구현된 병합 엔진 `RigRegeneration`은 제품 계층에서 중립 IR 내용으로 비교하며, `ThreeWayMerge`는 생성 결과 재정의(`GeneratedOverrides`)에만 씁니다.

### 5.1 이 모델로 기존 특수 사례 다시 서술하기

- **분할**: 원본 이미지가 바뀌는(원래 레이어를 파츠가 대체하는) B 분류 트랜잭션입니다. 파츠는 원래 메시의 사용자 차이(M − G, 분할된 정점 출처를 거침)를 이어받습니다. G′에서 파츠는 일반 레이어의 생성 결과입니다. v2 2회 캡처의 목적(파츠가 생성에 참여하고, 레코드는 생성 밖의 작성 데이터만 저장)은 한 번의 병합으로 달성되며, 승객, 주차, 분할 기록의 재생 메커니즘은 그에 따라 일상 경로에서 빠집니다.
- **뼈대**: 뼈대 베이크는 생성기에 속하며 출력은 G에 들어갑니다. 뼈를 바꾸는 것은 B 분류 트랜잭션입니다(팔다리별 재베이크를 그대로 사용). 관절 행은 토폴로지 마이그레이션이며, 바인딩 메시에 대한 사용자 수정은 병합 규칙에 따라 옮겨지므로 토폴로지 잠금과 베이크 전 파츠 디코딩이 더 이상 필요 없습니다. 사용자가 바인딩 메시를 뼈가 아닌 디포머로 재부착하면 여전히 모디파이어 `skeleton.skin`이 스키닝합니다.
- **머리카락 시뮬레이션, 팔 늘어뜨림 Warp 소멸**: G′에서 디포머가 사라지면 그 아래의 사용자 객체는 “M에만 있음”에 따라 재부착되며, 이는 `VanishedParent`의 일반형입니다.
- **생성 마이그레이션**: `rig_generation_transition`은 마이그레이션을 저널에 쓰고 재생할 때마다 실행합니다. 한 번의 병합으로 바꾸면 마이그레이션 결과가 곧 M′입니다.

## 6. 저장

설계안은 이를 “프로젝트 형식 v3”라고 불렀습니다. 실제 구현은 여전히 v2 아카이브이며, 체크포인트를 포함한 리비전은 리비전 schema 3으로 올라가고, 리그 객체는 내용 주소 방식으로 `rig/objects/<sha256>.bin`에 저장되며(종류별 디렉터리 없음), 리비전의 작성 리그 인덱스는 선택 사항인 `rig/revisions/`에 있습니다(10장과 [프로젝트 형식 · 체크포인트](PROJECT_FORMAT.md#체크포인트) 참고). 아래 표는 원래 설계입니다.

| 경로 | 내용 |
| --- | --- |
| `rig/objects/<类型>/<sha256>.bin` | 단일 객체의 영구 인코딩: 파라미터 목록과 파라미터 트리, 파츠 트리, 각 디포머, 각 메시(메시, 키폼, 채널, 블렌드 폼), Glue, 경로, 정점 그룹, 캔버스와 메타데이터 |
| `history/revisions/<key>.json` | `rig: {materialized: {...}, generated: {...}, meta}`를 추가해 M과 G의 객체 해시를 나열. 서로 다른 리비전 사이, M과 G 사이에서 내용에 따라 객체를 공유 |

- **인코딩**: 중립 IR(`format-model`, MIT)을 기반으로 schema 버전이 있는 영구 인코딩을 정의하고, 전방 마이그레이션과 코퍼스 회귀 테스트를 갖춥니다. `RigIrBinary`는 캐시 형식으로 자기 버전만 받아들이며 영구 형식으로 쓰지 않습니다. 부동소수점 역시 원래 비트대로 저장합니다.
- **텍스처**: M, G는 캔버스 단위 텍스처 좌표를 저장하며, 열 때 아틀라스에 바인딩합니다(`UvBinding`의 환산을 그대로 사용). 아틀라스는 여전히 문서가 결정합니다.
- **크기**(tml, 리그 전체 하나, `RigIrBinary`):

| | 원본 | deflate | `PuppetModel`로 디코딩 |
| --- | ---: | ---: | ---: |
| 뼈대 없음 | 약 336 KB | 약 174 KB | 약 3.5 ms |
| 자동 뼈대 | 약 7.1 MB | 약 5.6 MB | 약 26 ms |

  뼈대 리그의 크기는 주로 뼈 파라미터 위의 메시 키폼이며, 부동소수점은 압축률이 낮습니다. 객체 단위로 주소를 매기면 A 분류 편집은 바뀐 객체만 씁니다. 뼈를 다시 베이크하면 해당 팔다리의 바인딩 메시를 다시 씁니다.
- 저널 노드는 그대로 저장하며 명령 기록으로 씁니다.

## 7. 호환과 마이그레이션

- **v2 프로젝트 열기**: 헤드 리비전을 기존 재생 파이프라인(레거시 재생 경로로 고정)으로 한 번 재생해 M과 G를 얻고 다음 저장 때 씁니다. 재생에 실패하면 복구 상태로 열고, 실패한 항목을 나열하며, 더 이전 리비전으로 전환할 수 있게 합니다.
- **그 밖의 리비전**: 처음 전환할 때 같은 경로로 실체화합니다. 실체화되지 않은 리비전은 v2 문서 노드를 유지합니다.
- **레거시 재생 경로**: v1/v2 분할 기록, 레거시 형식 정적 필드, 생성 마이그레이션 레코드, `VanishedParent`와 승객 허용 오차를 별도 패키지로 옮겨 복구만 하고 새 기능과 함께 확장하지 않습니다. 저장된 프로젝트(`legacy-split.psd2live`, `v1-sample.psd2live`)로 IR 해시를 고정합니다. 이 경로는 여전히 현재 생성 코드를 호출하므로 이전 리비전의 실체화 결과가 생성 코드에 따라 달라질 수 있지만, 각 리비전은 한 번만 실체화합니다.
- **G가 없는 리비전**(실체화 이전의 오래된 리비전, 가져온 뒤 첫 재생성): 저장된 생성 입력을 현재 코드로 다시 생성해 G로 씁니다. 따라서 생성 코드의 차이는 사용자 수정으로 간주되어 유지되며, 데이터를 잃지 않습니다.
- **가져온 CMO3 모델**: G는 가져오기 기준선이며 재생성에 참여하지 않습니다.

### 8.1 테스트

- 실체화 일관성: 테스트 코퍼스에 대해 실체화 결과로 연 것과 재생으로 재빌드한 것이 같은 IR 해시를 가집니다.
- 병합: 손으로 작성한 작은 리그에서 5장의 모든 규칙을 다룹니다(디포머 소멸, 파라미터가 삭제되었지만 사용자 키폼이 있음, 관절 행 삽입, 사용자 토폴로지와 생성 토폴로지가 동시에 바뀜, 사용자가 삭제한 생성 객체, 사용자가 만든 Warp의 부모 소멸).
- 형식: 리비전 schema 3의 분할과 재결합이 무손실, 객체 공유, schema 마이그레이션, 이전 프로그램이 필드를 버리지 않고 더 높은 schema를 거부.
- 예제 PSD에서 파이프라인 전체를 돌리는 비교는 개발 도구로 만들고 전체 테스트에는 넣지 않습니다.

## 9. 위험과 미결 사항

- **크기**: 뼈대를 자주 조정하는 긴 히스토리는 바인딩 메시 사본을 여러 개 쌓게 되므로 실측이 필요합니다. 현재 저장은 헤드, 분기 끝, 체크포인트가 없는 리비전에 대해서만 작성 리그를 유지하고, 그 밖의 리비전은 마지막 체크포인트에서 빌드합니다([프로젝트 형식 · 작성 리그](PROJECT_FORMAT.md#작성-리그) 참고).
- **생성 개선이 더 이상 자동으로 반영되지 않음**: 인터페이스에서 프로젝트가 쓰는 생성기 버전을 알리고, “생성 업데이트” 진입점과 시험 실행 보고를 제공해야 합니다. 이는 제품 차원의 절충입니다.
- **분류는 여전히 코드에 따라 바뀜**: 열 때 원본 이미지를 분석한 결과는 인터페이스와 프리셋에만 영향을 주고 M에는 영향을 주지 않습니다. 프리셋은 실행 시 현재 분석을 읽으며, B 또는 C 분류 작업에 속합니다.
- **메모리**: 각 히스토리 노드의 M은 소프트 참조로 캐시하며, 적중하지 않으면 저장소에서 디코딩합니다(뼈대 리그 약 26 ms).
- **MCP**: 공개 명령은 바뀌지 않습니다. 새로 추가되는 재생성 시험 실행과 `workspace_inspect`의 병합 문제에는 엄격한 `resultSchema` / `jobResultSchema`를 선언해야 합니다.
- **결정됨**: `generationSource` 고정은 실체화 후에도 유지합니다. 재생성이 일어나지 않는 편집(페인팅, 이미지 교체)은 생성 결과를 바꾸지 않습니다. 재생성(분할, 프리셋 전환, 뼈대, “생성 결과 업데이트”)은 고정된 픽셀로 G′를 생성하며, 고정 이후에 추가된 레이어는 현재 픽셀을 쓰므로, 페인팅이 다음번의 무관한 재생성에서 생성기의 변화로 취급되지 않습니다. 유일한 예외는 생성 규칙 자체를 바꾸는 것(생성 설정과 분류)으로, 이는 현재 픽셀로 G′를 생성하되 메시 입력은 저장된 것을 그대로 씁니다(`RigGenerationChange`). 그리기 순서 재정의와 부모 재정의는 모두 생성 입력이며 B 분류에 속합니다. 기반 생성이 이를 읽으며, 생성된 모델이 이를 바꿀 때 재생성 병합을 하고 체크포인트를 씁니다(`WorkspacePreviewBuilder.normalizeMeshEdits`. 테스트 `paintingNeverReachesTheGenerationAndAnUpdateFindsNothingToDo`, `parentAndDrawOrderOverridesRegenerate`).

## 10. 구현 진행 상황

**0단계(구현됨)**

- 뼈에 바인딩된 메시에 대해, 저널의 정점 인덱스 레코드가 모두 세분화 전 정점 수로 쓰였다면 뼈대가 더 이상 그 메시에 관절 행을 삽입하지 않습니다(`SkeletonCanvasSkin.lockedTopology`). [문서 계층 · 저널이 배치한 메시](DOCUMENT_LAYER.md#저널이-배치한-메시) 참고.
- 머리카락 시뮬레이션이 기존 흔들림 Warp를 삭제할 때, v2 분할 파츠가 기반 메시와 함께 추종 Warp로 재부착됩니다(`RigBuilder`). “정지 Warp 유지”는 채택하지 않았습니다. 그렇게 하면 이미 베이크된 머리카락 시뮬레이션이 놓인 부모 공간이 바뀌기 때문입니다.

**1–2단계(핵심 구현됨)**

- 재생을 두 단계로 나눕니다(`RigEditOverlay.replayAuthored` / `finish`). `BuiltRig.authoredRig`는 작성 리그(`AuthoredRig`: 작성 puppet, 저널이 만든 메시의 매핑, 레이어 표시 여부를 적용해야 할 메시)를 주고, `AuthoredRig.finished`는 모디파이어, 재정의 병합, 지연된 패널 편집, 표시 여부와 그리기 순서를 실행합니다. `withRigEdits`는 두 단계를 이은 것이며, 내보내기는 이전과 바이트 단위로 일치합니다(`ExportGoldenTool`).
- `RigPreviewModel`의 기반 리그와 작성 리그는 `PreviewRigSources`가 제공합니다. 생성 빌드는 기반 리그를 이미 알고 있고, 작성 리그는 처음 쓸 때 재생 체크포인트가 줍니다. 작성 리그로 빌드한 모델은 누군가 `baseRig`를 읽을 때만 기반 리그를 생성합니다.
- `PSD2LivePipeline.materializedPreview`: 작성 리그로 미리보기를 빌드하며, 원본 이미지 분석과 아틀라스 패킹만 하고 `RigBuilder`, 뼈대 베이크, 저널 재생은 실행하지 않습니다. 아틀라스 바인딩 키가 다르면 빈 값을 반환하고 호출자가 평소대로 빌드합니다. 지연 삭제(소프트 삭제된 레이어)가 있는 문서도 지원하며, 가져온 CMO3 모델은 지원하지 않습니다.
- 리비전별 저장소(`project/MaterializedRigStore`): 이 프로세스가 빌드한 리비전(소프트 참조)과 아카이브를 열 때 읽은 리비전. `WorkspacePreviewBuilder.build`는 먼저 저장소를 조회하며(열기, 히스토리 전환, 실행 취소), 현재 모델을 더 싸게 업데이트할 수 있는 경우(3단계 참고, 또는 기반 리그를 이미 가지고 있고 편집 오버레이만 바뀐 경우)는 예외입니다. 저장은 얻을 수 있는 리비전을 아카이브의 `rig/`에 씁니다(형식은 [프로젝트 형식 · 작성 리그](PROJECT_FORMAT.md#작성-리그) 참고).
- 영구 인코딩: `RigIrObjects`(MIT)가 중립 IR을 프레임, 디포머, 메시 객체로 나누며 버전별로 읽을 수 있습니다. `MaterializedRigCodec`이 헤더를 씁니다.

**3단계(추가 편집 구현됨)**

- 새 문서의 작성 단계 입력이 현재 모델과 같고 저널 끝에 항목만 추가된 경우(`RigEditOverlay.extends`. 추가된 것이 `art_primitive` 레코드가 아님), `PSD2LivePipeline.updateRigEdits`는 추가된 항목을 재생 의미대로 현재 작성 리그에 적용하고(`appendedTo`) 마무리 단계를 실행합니다. 기반 리그를 읽지 않으며, 그 이전 항목도 재생하지 않습니다. 결과의 기반 리그는 현재 모델의 것을 그대로 씁니다(여전히 필요할 때 생성).
- 커밋 경로에서 더 이상 불필요하게 기반 리그를 생성하지 않습니다. 생성 결과 재정의의 캡처는 저널에 `art_primitive` 레코드가 있을 때만 기반 리그의 분할 파츠를 읽습니다(`RigPreviewModel.primitiveSkins`).
- 따라서 작성 리그로 연 프로젝트에서는 캔버스와 MCP의 기하, 키폼, 구조, 정점 그룹, 경로 등의 편집이 생성을 일으키지 않습니다. 생성 입력 변경과 분할은 여전히 기반 리그를 거칩니다(병합에 G와 G′가 필요).

**3단계(구현됨)**

- 생성된 모델의 첫 편집은 원래 저널 끝, 새 항목 앞에 현재 작성 리그의 체크포인트를 쓰고, 이후 마지막 체크포인트 뒤에 편집이 32개(`RigEditOverlay.CHECKPOINT_INTERVAL`) 쌓이면 하나를 더 씁니다. 생성 스냅샷은 이전 체크포인트의 것을 이어받고, 없으면 기반 리그를 씁니다. 따라서 어떤 빌드든 최대 32개와 이번 편집의 항목만 재생합니다.
- 이전 항목을 고쳐 쓰는 편집(드래그 병합, 생성 결과 재정의의 캡처, 실행 취소와 다시 실행)은 저장된 리비전이나 체크포인트 이후의 항목에서 작성 리그를 얻습니다(`RigPreviewModel.authoredWithoutBase`, `PSD2LivePipeline.updateRigEdits`). 기반 리그를 생성하지 않으며 재생 체크포인트도 거치지 않습니다.
- 시뮬레이션 베이크, 다시 베이크, 비교는 작성 리그가 마무리 단계를 거친 결과를 읽습니다(`SimAuthoring.AuthoredRigs`). 기반 리그를 생성하지 않습니다.
- 실측(tml 예제, 런타임으로 구조 편집 40회 연속): 첫 편집 약 190 ms(체크포인트 쓰기 포함), 이후 매번 약 20–40 ms, 33번째 항목의 체크포인트 약 50 ms. 콜드 빌드 약 170 ms, 기반 리그를 생성하지 않음.

**4단계(구현됨)**

- 병합 엔진 `RigRegeneration.merge(G, G′, M)`은 5장에 따라 병합합니다. 객체는 ID로 맞추고, “바뀌었는지”는 중립 IR의 내용으로 판정합니다. 기하 잔차는 `PrimitiveResidual`(v2 분할의 잔차 도구)로 새 부모 공간으로 바꾸고 캔버스 텍스처 좌표로 새 정점에 마이그레이션하며, 정점 그룹, 경로, Glue 정점 쌍도 함께 마이그레이션합니다. 사라진 생성 디포머는 기본 포즈에서 접힌 뒤 펼쳐지고(umamo `withDeformerDeleted`), 그 아래의 사용자 객체는 위로 올라갑니다. 문제는 종류별로 보고합니다. G와 G′는 `BuiltRig.resolvedPuppet`(v2 파츠 배치 완료)을 쓰므로, 기반 생성이 파츠를 위해 한 재부착과 스키닝도 생성 결과로서 병합에 참여합니다. v1 파츠는 레코드로만 만들어집니다. 어느 한쪽 뼈대가 그것을 스키닝했으면 그 레코드를 G와 G′ 위에서 각각 저널 방식으로 재생하며(G′는 새 기반의 `PrimitiveSkins` 사용), 뼈대가 준 스키닝과 용접 Glue도 생성 결과로 병합합니다. 어느 한쪽이라도 재생에 실패하면 양쪽 모두 배치하지 않고, 파츠는 사용자 객체로 유지됩니다. 생성 마이그레이션(`rig_generation_frames`)이 메시를 생성 디포머의 이름 바꾼 사본(`GenerationFrame<n>_…`) 아래로 옮긴 뒤에는, G와 G′를 마지막 마이그레이션 레코드의 `frames`에 따라 이름을 바꾼 다음 병합합니다(`RigGenerationFrames.named`). 그렇지 않으면 모든 메시가 사용자가 부모를 바꾼 것으로 취급됩니다. 체크포인트가 저장하는 생성 결과는 여전히 생성기의 원래 출력입니다. 블렌드 폼은 파라미터별로 3방향 병합하며, 병합된 기하와 같은 부모 공간과 토폴로지에 있어야 합니다. 기하가 G′를 취하면 사용자의 형태는 잔차의 부모 공간 환산을 거쳐 옮겨지고, 기하가 M을 유지하면 다른 부모 공간에서 생성된 형태는 채택하지 않습니다(`dropped` 보고. 사용자의 같은 이름 형태는 유지).
- 체크포인트: 저널 레코드 `rig_checkpoint`가 병합된 작성 리그(객체는 내용 주소 방식, 문서와 함께 영구 저장)와 병합 문제를 저장합니다. 재생은 마지막 체크포인트에서 시작하고 그 앞의 항목은 히스토리로만 남습니다. 아틀라스가 바뀌면 실체화된 리그를 캔버스 텍스처 좌표로 다시 바인딩합니다. [문서 계층 · 체크포인트](DOCUMENT_LAYER.md#체크포인트)와 [프로젝트 형식 · 체크포인트](PROJECT_FORMAT.md#체크포인트) 참고.
- 트리거: 편집이 현재 저널을 이어 가고, 새 문서의 기반 생성 결과(이전 항목이 보는 것)가 현재와 다르면 병합하고 경계에 체크포인트를 씁니다. 이전 항목이 새 결과 위에서 재생될 수 있는지와는 무관합니다. 머리카락 시뮬레이션 프리셋도 내부적으로 똑같이 합니다.
- 런타임은 재빌드가 삽입한 체크포인트를 커밋에 합칩니다. 일괄 처리 구성원은 앞 후보로부터 빌드합니다. 마지막 체크포인트의 문제가 `workspace_inspect`의 `quality.regeneration`에 들어갑니다.
- 형식: 체크포인트를 포함한 리비전은 리비전 schema 3이며, 인덱스가 그 리그 객체를 나열하고 아카이브는 `rig/objects/`에 보관합니다. 이전 프로그램은 이런 프로젝트를 거부합니다.
- 생성된 모델은 뼈대를 켠 뒤 더 이상 저널에서 정점 그룹을 다시 샘플링하지 않으며, 병합이 마이그레이션합니다.
- 생성 설정과 분류: 생성된 모델은 편집을 준비할 때 병합하고 체크포인트를 쓰며, G′는 현재 원본 이미지로 생성합니다. 더 이상 `rig_generation_transition`, `rig_generation_frames`, 마이그레이션에 따라 만든 메시 레코드를 쓰지 않습니다. `rig_generation_baseline`은 그 뒤에 체크포인트가 없을 때만 기반 생성을 제약합니다.
- 분할(5.1절): G와 M의 원래 메시를 분할 자체가 같은 파츠로 자르고, 파츠가 원래 레이어를 대체한 뒤의 G′와 병합합니다. `art_primitive` 레코드(생성된 원래 메시는 선언만 하는 버전 2, 저널이 만든 원래 메시는 버전 1) 바로 뒤에 체크포인트가 오며, 레코드는 재생하지 않습니다. 2회 캡처, 가드, 버전 1 폴백, `psd2live.artPrimitiveV2` 스위치와 명시적 업그레이드 명령은 삭제했습니다.
- 시험 실행: `workspace_preview_regeneration`(읽기 전용 백그라운드 작업)은 1–128개 문서 작업에 대해 커밋과 같은 후보 준비와 재빌드를 하고, 쓰게 될 체크포인트(`regeneration`은 병합 문제 포함, `materialized`는 새 항목 앞에서 실체화된 작성 리그)와 추가·삭제되는 객체를 보고하며, 상태, 히스토리, 리소스를 게시하지 않습니다. 같은 state에서 같은 작업을 커밋하면 같은 후보 리비전을 얻습니다.
- 체크포인트는 그것이 기반한 생성 스냅샷 G′도 함께 저장합니다(작성 리그와 바뀌지 않은 객체를 공유). “생성 업데이트”(`rig_update_generation`, GUI “모델 → 생성 결과 업데이트”)는 마지막 체크포인트의 생성 스냅샷을 G로, 이 프로그램이 지금 같은 입력으로 생성한 결과를 G′로, 현재 작성 리그를 M으로 병합하고, 저널 끝에 새 체크포인트를 씁니다. 생성 결과가 같으면 커밋하지 않습니다.
- 실측(v2 분할과 프리셋 정점 그룹이 있는 사용자 프로젝트 하나): 병합 결과와 완전 생성 후 재생한 결과가 기본, 머리 회전, 몸 회전 포즈에서 점 단위로 일치합니다(뒷머리 시뮬레이션 켜기, 자동 뼈대 켜기 두 경우 모두 차이 0). 병합 10–15 ms. 런타임으로 뒷머리 프리셋과 자동 뼈대를 차례로 적용: 각각 체크포인트 하나를 쓰고, 분할 파츠가 추종 Warp로 재부착되며, 병합 문제 없음. 저장 약 7.2 MB(원래 6.3 MB), 콜드 열기 후 헤드 빌드 약 0.6 s, 결과가 비트 단위로 일치, 기반 리그를 생성하지 않음.

**설계와의 차이**

- 생성 입력 변경이 일으키는 재생성은 현재 프로그램으로 현재 문서의 G를 다시 생성합니다(체크포인트에 저장된 G를 쓰지 않음). 따라서 프로그램 변경에서 오는 차이는 사용자 수정으로 간주되어 유지되며, 새 버전 생성기의 개선은 “생성 업데이트”를 통해서만 프로젝트에 들어갑니다.
- 리비전의 작성 리그 인덱스(`rig/revisions/`)는 선택 데이터이지만(없으면 평소대로 빌드), 있으면 그 리비전의 데이터로 씁니다. 아틀라스 바인딩 키가 다르면 재생으로 돌아가지 않고 다시 바인딩하므로, 이 버전이 저장한 프로젝트는 열 때 재생에 의존하지 않습니다. 기준 데이터는 저널의 체크포인트입니다. 체크포인트가 없는 문서(이전 프로젝트, 또는 아직 생성 변화가 일어나지 않은 새 프로젝트)는 여전히 생성과 저널 전체 재생으로 빌드하므로, 레거시 재생 메커니즘(`VanishedParent`, 승객 허용 오차, v1/v2 분할 기록 등)은 유지됩니다.
- 분할은 파츠가 참여하는 프레임을 바꾸므로, 분할할 때마다 체크포인트를 하나 씁니다.

**5단계(구현됨)**

- 새 편집은 더 이상 기반 리그가 있어야 재생할 수 있는 레코드를 쓰지 않습니다(분할 기록 뒤에는 항상 체크포인트가 있고, 생성 마이그레이션은 병합으로 바뀜). 마지막 체크포인트 뒤에 이전 버전이 쓴 그런 레코드가 아직 있는 저널이면, 그것을 이어 가는 첫 편집이 먼저 현재 작성 리그를 원래 저널 끝에 실체화하며, 그 레코드들은 이때 한 번만 재생됩니다(`RigEditOverlay.replaysLegacy`).
- 레거시 재생과 가져온 CMO3 모델에서만 쓰는 코드는 `core.legacy`로 옮겼습니다(분할 기록 재생, 승객 허용 오차, 더 이상 생성되지 않는 부모, 생성 마이그레이션의 쓰기와 재생, 재생 체크포인트). [문서 계층 · 레거시 재생](DOCUMENT_LAYER.md#레거시-재생) 참고. 가져온 모델은 병합할 생성 결과가 없으므로 여전히 마이그레이션 레코드와 이전 분할을 쓰지만, 그것을 쓴 커밋이 바로 뒤에 체크포인트를 씁니다. 이 레코드들은 자기 빌드에서만 한 번 재생됩니다.

- 가져온 CMO3 모델도 첫 편집과 32개마다 체크포인트를 씁니다(생성 스냅샷 없음: G는 가져오기 기준선이며 다시 생성하지 않음). 빌드는 가져오기 기준선 위에서 체크포인트부터 재생하므로 재생량이 마찬가지로 제한됩니다. 이들은 작성 리그만으로 빌드하지 않으며(텍스처 좌표가 가져온 텍스처 페이지로 주소가 매겨지고 바인딩 키가 없음), 생성 설정 변경은 여전히 마이그레이션 레코드를 씁니다(7장). 분할, 깊이 분할, 마이그레이션 등 가져오기 기준선 위에서 재생해야 하는 레코드는 그것을 쓴 커밋이 바로 뒤에 체크포인트를 쓰며(`WorkspacePreviewBuilder.importedRecordsCheckpointed`), 이후의 빌드, 열기, 실행 취소는 더 이상 그것을 재생하지 않습니다(`ImportedSplitCheckpointTest`).
- GUI: “모델 → 생성 결과 업데이트 미리 보기”는 같은 시험 실행 보고로 업데이트가 리그를 바꿀지와 확인해야 할 항목을 알려 주며 커밋하지 않습니다. 결과는 “생성 결과 업데이트”의 결과와 마찬가지로 저널 패널에 기록됩니다(편집 중에는 상태 표시줄이 캔버스 안내에 쓰임). 데스크톱 프로그램 실측(Xvfb, 소프트웨어 렌더링, tml 가져온 뒤 MCP로 편집): 첫 편집이 생성 스냅샷을 포함한 체크포인트를 쓰는 데 약 0.3 s, 두 메뉴 항목이 그에 따라 활성화되고, 미리보기는 “생성 결과에 변화 없음”을 보고하며, `workspace_preview_regeneration`은 머리·몸 강도 수정에 대해 `regeneration` 체크포인트 하나를 보고하고 프로젝트 상태는 바뀌지 않습니다.

**실측**(리비전 6개를 포함한 사용자 프로젝트 하나, 뼈대 없음): 헤드 리비전을 생성과 재생으로 빌드하면 약 2.2 s, 저장된 작성 리그로 콜드 열기 후 빌드하면 약 0.4 s, IR 해시 일치. 아카이브 약 0.3 MB 증가.

**테스트**: `SplitMergeRulesTest`(수정되지 않은 원래 메시를 생성된 파츠로 분할. 원래 메시에 대한 사용자의 이동이 파츠로 옮겨지며 절단선은 캔버스에 그린 위치를 따름. 이후 설정을 바꿔 재생성해도 이동이 유지됨), `LegacyMaterializeOnceTest`(`legacy-split.psd2live`의 첫 편집이 원래 저널 끝에 한 번 실체화하고, 결과가 이전 레코드 재생과 일치하며, 콜드 빌드가 더 이상 재생하지 않음), `LegacyReplayBoundaryTest`(`core.legacy`를 참조하는 파일이 알려진 분기 지점으로 한정됨), `ImportedEditCheckpointTest`(가져온 모델의 체크포인트가 완전 재생과 일치), `AuthoredEditCheckpointTest`(첫 편집과 32개마다 체크포인트를 쓰고, 콜드 빌드와 이전 항목 고쳐 쓰기가 모두 기반 리그를 생성하지 않으며, 결과가 체크포인트를 제거한 뒤 완전 재생한 것과 일치), `RegenerationPreviewTest`(시험 실행이 재생성 체크포인트를 보고하고 게시하지 않으며, 커밋이 같은 후보 리비전을 얻음), `RegenerationCheckpointTest`(런타임으로 머리카락 시뮬레이션 켜기: 체크포인트가 원래 저널 끝에 있고 파츠가 위치 변화 없이 재부착됨. 콜드 빌드가 체크포인트 이전의 잘못된 항목과 무관. 기반 리그 없는 빌드와 아틀라스 교체 시 재바인딩. 실행 취소, 다시 실행, schema 3으로 저장 후 콜드 열기. 생성 업데이트가 생성기의 새 출력을 채택하면서 사용자 파츠를 유지하고, 두 번째 업데이트는 커밋하지 않음), `WorkspaceInspectionContractsTest`(`quality.regeneration`), `RigRegenerationTest`(수작업 리그 위의 병합 규칙: 양쪽 모두 바뀌지 않음, 사라진 Warp 아래의 사용자 메시, 재부착에 따라 마이그레이션되는 사용자 키폼, 버려졌지만 여전히 쓰이는 파라미터, 세분화된 메시의 정점 그룹과 키폼, 사용자 삭제와 충돌), `MaterializedPreviewTest`(작성 리그 빌드와 완전 빌드의 IR 해시 일치, 기반 리그를 생성하지 않음, 아틀라스가 다르면 거부, 항목 추가에 기반 리그가 필요 없음), `MaterializedRigProjectTest`(저장 후 콜드 열기한 각 리비전이 모두 작성 리그로 빌드되며 일치. 저널을 더 이상 재생할 수 없는 리비전도 작성 리그로 열 수 있음), `RigIrBinaryTest`(객체 분할, 재결합, 공유, 거부), `SkeletonCanvasSkinTest`.

## 11. 구조 승계와 병합 충실성

### 11.1 문제

재생성이 구조(부모, 토폴로지, 디포머 삽입이나 삭제)를 바꾸는데 사용자 데이터는 이전 구조로 표현되어 있는 것은 반복해서 나타나는 문제입니다(`2d6d0b7d`, `5019b69b`, `18f24b89`, `9eff1d60`, `e72fc541`, `da426e1f`, `7f30f7aa` 등). 체크포인트 모델에서 이 문제에는 세 가지 공통 원인이 있습니다.

1. **병합은 차이로 의도를 추론하므로, 오류가 스스로 굳어 버립니다**: “사용자가 바꿨는지”는 M과 G의 비트 비교로 판정합니다. 한 번의 병합이 생성기의 구조 변화를 객체에 옮기지 못하면(M′ ≠ G′인데 사용자는 바꾸지 않음), 다음 병합은 이 차이를 사용자 수정으로 보고 유지하며, 다시는 생성기를 따르지 않습니다. 사례: 사용자가 토폴로지를 재빌드한 소매가 뼈대를 켤 때 “사용자 토폴로지 유지”에 따라 더 이상 생성되지 않는 `DeformArmHang_L/R` 아래에 남았다가 호흡 Warp로 접혀 들어가 뼈 스키닝을 잃었습니다. 이후 매번 병합할 때마다 “사용자가 재부착함”으로 보고되었습니다.
2. **생성기는 객체가 어디로 갔는지 알지만, 병합은 추측할 수밖에 없습니다**: 뼈대의 몸통 Warp가 호흡 Warp 위의 모든 내용을 넘겨받고, 뼈대를 켤 때 뼈가 팔 늘어뜨림 Warp를 승계하지만, 이 관계는 생성 결과와 함께 출력되지 않으므로 병합은 조상 체인을 따라 가까운 곳으로 재부착하는(`VanishedParent`, `rehomed`) 식의 휴리스틱만 쓸 수 있습니다. 사례: 가져온 뒤 호흡 Warp에 바인딩한 이미지가 몸통 Warp에 들어가지 않아 상체 회전을 따라가지 않았습니다.
3. **설계와 구현 사이의 공백이 조용합니다**: 5장은 사용자가 토폴로지를 바꿨을 때 “G에 대한 G′의 생성 변화를 마이그레이션 계획으로 사용자 토폴로지에 매핑”하도록 규정하지만, 구현은 M을 통째로 유지할 뿐이며 문제는 표시되지 않는 보고에 warning으로 기록되었습니다.

### 11.2 방안

네 계층으로 처리하며, 앞 계층의 실패는 뒤 계층이 받쳐 주거나 발견합니다.

| 계층 | 내용 | 해결 |
| --- | --- | --- |
| 뼈 작용을 상태로 판정 | `skeleton.skin`이 스키닝하는 메시에는 저널 레코드가 배치한 것(`placedByRecords`) 외에, 마지막 체크포인트의 작성 리그에서 자기 팔다리의 어떤 뼈에도 구동되지 않는 바인딩 메시(`SkeletonCanvasSkin.unskinned`: 부모 체인에 그 팔다리의 뼈 디포머가 없고, 메시에도 그 팔다리 파라미터의 키폼 축이나 블렌드 폼이 없음)도 포함됨. 베이크는 여전히 레코드만으로 어떤 메시를 재부착하지 않을지 결정 | 메시가 어떻게 거기에 도달했든(레코드, 병합, 이전 버전) 바인딩된 메시는 항상 뼈를 따라 움직임. 뼈 아래에 있으면 베이크가 구동하고, 그렇지 않으면 캔버스에서 스키닝 |
| 뼈대 작용 검사 | 관찰 보고 `quality.skeleton`(`SkeletonBindingQuality`): 뼈에 바인딩되었지만 뼈가 구동하지 않는 메시(`SKELETON_BINDING_INEFFECTIVE`, warning), 호흡 Warp 아래에 있으면서 몸통 Warp를 우회하고 몸 절반을 축으로 삼지 않는 메시(`SKELETON_TORSO_BYPASSED`, warning), 리그에 없는 메시에 대한 바인딩(`SKELETON_BINDING_MISSING`, info) | 조용한 실패가 보이게 됨 |
| 승계 | 병합이 G와 G′에서 생성기가 어느 디포머의 내용을 어디로 넘겼는지 읽어 냄(예: 호흡 Warp의 내용 → 몸통 Warp, 팔 늘어뜨림 Warp → 해당 팔 뼈. [11.3](#113-승계) 참고). 사용자가 만들거나 재부착한 객체는 그에 따라 재부착. 사용자가 토폴로지를 바꿨고 생성 측이 부모나 기하를 바꿨으면 새 부모를 취하고 생성 변화를 캔버스 텍스처 좌표로 사용자 토폴로지에 매핑(5장 보완) | 병합이 더 이상 구조의 행방을 추측하지 않음 |
| 병합 충실성 | 불변식: M′의 어떤 값 ≠ G′ ⇒ M의 같은 값 ≠ G(사용자가 바꾸지 않은 값은 새로 생성된 값과 같음). 테스트에서 단언하고, 런타임에 위반되면 G′를 취하고 보고. 또한 “A 다음 B / B 다음 A” 순서 행렬로 B 분류 작업과 A 분류 작업의 조합을 테스트. 마지막으로 충실했던 체크포인트부터 다시 병합하는 복구 작업 제공 | 병합 오류가 더 이상 스스로 굳어지지 않으며, 이미 손상된 프로젝트를 복구할 수 있음 |

**진행 상황**: 네 계층 모두 구현되었습니다. 11.3, 11.4 참고. 테스트: `SkeletonCanvasSkinTest.aMeshACheckpointHoldsOutsideItsBonesTurnsWithThemWithoutARecord`, `SkeletonBindingQualityTest`, `RigRegenerationTest`(승계, 사용자 토폴로지, 다시 병합), `RegenerationOrderTest`(순서 행렬).

### 11.3 승계

승계 관계는 따로 저장하지 않고, 병합이 G와 G′ 자체에서 읽어 냅니다(`RigRegeneration.successors`). G에서 디포머 D 아래에 있고 G′에도 여전히 있는 객체들이 G′에서 모두 같은 X ≠ D 아래에 있고, D가 G′에 더 이상 없거나(뼈대를 켠 뒤 더 이상 생성되지 않는 팔 늘어뜨림 Warp), X가 G′에 새로 추가되어 D 아래에 있는 디포머(뼈대가 호흡 Warp 아래에 삽입한 몸통 Warp)인 경우입니다. 객체가 여러 부모로 흩어지면 승계로 인정하지 않습니다. 사라진 D가 내용을 자기 부모에게 넘겼다면 평소대로 `rehomed`로 접습니다. 따라서 이미 저장된 체크포인트(모두 G를 가지고 있음)는 형식을 바꾸지 않고도 쓸 수 있으며, 규칙도 특정 생성 단계의 약속에 의존하지 않습니다.

병합할 때, 사용자가 만든 객체와 사용자가 재부착한 객체는 부모가 승계되면(여러 단계에 걸쳐도 됨) 그에 따라 재부착됩니다. 메시는 구조 편집 `bind`의 `space=canvas` 방식으로 기본 포즈에서의 캔버스 위치를 유지하고(`RigStructureEdits.carriedToParent`), 디포머는 재부착이 그 아래 어떤 메시의 정지 위치도 바꾸지 않을 때만 재부착합니다. 그렇게 할 수 없으면 그대로 두고 `conflict`를 보고합니다(부모가 이후 사라지면 이전처럼 접음).

뼈대가 있는 실제 프로젝트에서 뼈대를 켤 때의 병합을 다시 실행한 결과: 토폴로지를 재빌드한 소매가 팔 뼈 아래로 들어가 사용자의 정점을 유지하고, 그 위의 뼈 키폼과 블렌드 폼(포즈, 아래팔, 손)이 함께 마이그레이션되며, 정지 위치 편차는 0.01 px 미만입니다. 가져온 뒤 호흡 Warp에 바인딩한 이미지와 앞뒤로 층을 나눈 상의 파츠가 승계에 따라 몸통 Warp에 들어가 상체 회전을 따라갑니다.

### 11.4 병합 충실성과 복구

- **품질 저하를 사용자 선택으로 취급하지 않음**: 사용자가 토폴로지를 바꿨고 생성 측이 부모를 바꿨으면 차례로 시도합니다. 텍스처 좌표로 생성 변화를 사용자 정점에 매핑합니다(`topology_followed`). 매칭되지 않으면 여전히 사용자 메시를 캔버스 위치대로 새 부모 아래에 붙이고, 생성 측이 아닌 사용자 자신의 키폼을 가져갑니다(`topology_kept`). 새 부모가 수용할 수 없을 때만 이전 부모를 유지하고, 이 부모가 사용자가 고른 것이 아님을 밝히는 `conflict`를 보고합니다.
- **사용자 정점 위의 블렌드 폼**: 사용자가 토폴로지를 바꾼 메시는 블렌드 폼을 G와 비교할 때 먼저 G의 블렌드 폼을 텍스처 좌표로 사용자 정점에 샘플링합니다. 정점 수가 다르다는 것 자체는 사용자 수정으로 치지 않습니다. 그렇지 않으면 G의 모든 블렌드 폼이 사용자의 것으로 간주되어 유지되고, 생성 측이 같은 파라미터를 키폼 축으로 바꿀 때(뼈대 조정 후 뼈가 블렌드 폼에서 키폼으로 바뀜) 둘이 겹쳐 메시가 두 번 움직입니다.
- **다시 병합**(`RigMergeRepair`, “생성 결과 업데이트” / `rig_update_generation`을 통해): 체크포인트는 병합 양쪽의 생성 결과를 저장하므로, 각 재생성 체크포인트에 대해 이 프로그램으로 병합을 다시 하고, 구조(각 객체의 부모, 메시의 정점 수, 키폼 축과 블렌드 폼)가 저장된 결과와 다르면 그 지점부터 바로잡습니다. 수정량(저장된 결과 → 지금 병합한 결과)은 3방향 병합으로 이후의 각 재생성 체크포인트의 입력에 옮겨지고(이 병합들은 이 프로그램으로 다시 함. 분할 체크포인트는 자체 병합 방식이 있으므로 수정을 그 결과에 바로 옮김), 마지막으로 현재 작성 리그에 옮겨지며, 이후의 편집은 유지됩니다. 구조만 비교하며, 재빌드가 반올림 오차 범위에서만 재현할 수 있는 수치는 다른 것으로 치지 않습니다. 다시 한 각 체크포인트는 `remerged`와 구조가 다른 객체를 보고합니다. 복구는 생성기 업데이트와 함께 새 체크포인트 하나로 쓰이며, 미리 보고 실행 취소할 수 있습니다. 복구가 쓴 체크포인트(`remerged` 포함) 이전의 수정은 모두 포함되어 있으므로, 이후에는 그것부터 다시 비교를 시작합니다. 수정이 현재 작성 리그의 구조를 바꾸지 않으면 더 이상 커밋하지 않으므로, 복구 후 다시 업데이트하면 “변화 없음”이 됩니다. “생성 결과 업데이트”가 쓴 체크포인트에 저장된 생성 스냅샷은 곧 병합에 쓴 G′(버전 1 파츠 포함)이며, 다른 재생성과 일관되므로 다시 병합할 때 스냅샷 불일치로 오판하지 않습니다.
- **능동적 발견**: 복구가 사용자가 메뉴를 찾는 데에만 의존해서는 안 됩니다. 저널의 체크포인트가 바뀐 뒤(프로젝트 열기, 재생성, 실행 취소) GUI는 백그라운드에서 검사합니다(`RigMergeRepair.stale`: 복구가 필요하고 수정이 현재 리그 구조를 바꾸는 체크포인트. 체크포인트 병합을 하나씩 다시 한 결과는 그 입력, 즉 마지막 생성 체크포인트와 그 이전의 저널, 아틀라스, 원본 이미지를 키로 캐시하며, 체크포인트 이후의 일반 편집은 마지막 병합만 하고 모든 체크포인트를 다시 하지 않음. 첫 검사는 체크포인트 수에 따라 늘어나며 실제 프로젝트에서 약 0.8 s). 발견하면 편집 캔버스 위쪽에 `NoticeBanner`로 알리고 「생성 결과 업데이트」「변경 사항 미리 보기」 버튼을 붙입니다. MCP는 `quality.regeneration`의 두 번째 검사로 `REGENERATION_REPAIR_AVAILABLE`을 얻습니다. `RegenerationOrderTest`는 이전 방식으로 병합한 뼈대 체크포인트를 구성해, 그것이 발견되고, 보고에 나타나며, 업데이트 후 사라지고, 다시 업데이트하면 커밋하지 않음을 확인합니다.
- **순서 행렬**(`RegenerationOrderTest`): 사용자가 소매 토폴로지를 재빌드하는 것과 뼈대를 추가하는 것을 두 가지 순서로 런타임을 통해 커밋한 뒤, 뼈를 움직여 두 번째 재생성을 일으킵니다. 각 순서에서 뼈대 작용 검사는 문제를 찾지 못하며, 뼈와 상체 모두 소매를 움직입니다. 이 절의 수정을 끄면 “재빌드 후 뼈대 추가” 순서에서 뼈가 작용하지 않는 문제가 재현됩니다.
- 뼈대가 있는 실제 프로젝트에서 “생성 결과 업데이트” 실행: 뼈대를 켤 때와 그 뒤 뼈를 움직일 때의 두 병합을 다시 하여, 소매가 팔 뼈 아래로 들어가 사용자 토폴로지를 유지하고, 가져온 이미지와 상의 파츠가 몸통 Warp에 들어가며, 뼈대 작용 검사는 비어 있고, 나머지 메시의 정지 위치 편차는 0.1 px 이하입니다. 동시에 앞뒤 층 분할로 대체된 뒤 남아 있던, 어떤 메시에서도 참조하지 않는 원래 메시 하나가 제거되었습니다(체크포인트가 저장한 생성 스냅샷이 그것에 대해 불일치했고, 다시 병합할 때 생성기에 따라 버려짐).
