# 프로젝트 형식 v2

[문서 목록](../../README.md) · [中文](../../zh/spec/PROJECT_FORMAT.md) · [English](../../en/spec/PROJECT_FORMAT.md) · [사용자 가이드](../guide/USER_GUIDE.md)

`.psd2live`는 UTF-8 JSON과 PNG 래스터 리소스를 담은 암호화되지 않은 ZIP입니다. 저장된 프로젝트는 원본 PSD 경로에 의존하지 않고 원본 소재와 히스토리를 함께 담습니다. `.psd2live.json`이라는 이름의 내보내기 보고서는 프로젝트가 아닙니다.

ZIP 항목 방식: PNG(`assets/`, `images/`, 뷰 이미지)와 CMO3 원본은 이미 압축되어 있으므로 `STORED`로 씁니다. 1 MiB 이상인 그 밖의 JSON이 아닌 파일(원본 PSD 등)은 먼저 샘플링하여, 가장 빠른 수준에서 샘플이 절반 미만으로 줄어들 때만 그 수준으로 DEFLATE하고 그렇지 않으면 `STORED`로 씁니다. JSON과 그 밖의 모든 항목은 이전처럼 DEFLATE합니다. `manifest.json`이 마지막 항목입니다. 항목은 이름순으로 정렬되고, 모든 수정 시각은 1980-01-01이며, 이름은 UTF-8입니다. 항목 수, 오프셋, 길이가 고전 ZIP의 한계를 넘으면 ZIP64 레코드를 씁니다. 작은 항목은 여러 스레드에서 미리 읽고 압축한 뒤 순서대로 씁니다. 다시 읽기와 열 때의 압축 해제도 항목 단위로 병렬 처리합니다. 리더는 어느 방식이든, 어떤 항목 순서든 받아들입니다. 모든 항목을 DEFLATE하고 매니페스트가 다른 항목 사이에 있던 이전 빌드의 아카이브도 그대로 열립니다. 방식과 항목 순서는 형식의 정체성에 포함되지 않으며, 매니페스트 해시는 압축되지 않은 바이트를 대상으로 합니다.

## 저장 상태와 프로젝트 교체

제목 표시줄의 `*`와 저장/버리기 확인 창은 아카이브에 기록되는 표시 상태와 별개로 프로젝트 내용을 추적합니다.

| 변경 | 저장 필요 |
| --- | --- |
| 원본 소재, 모델 편집, 생성/내보내기 설정, 출력 디렉터리, 히스토리 체크아웃 | 예 |
| 작성한 파라미터 포즈와 잠금, 스냅샷, 히스토리 주석, 타임라인 보조 도구(파라미터 북마크와 각 모션의 숨김·고정 트랙 및 마커), 캔버스 레이어/디포머 표시 여부, 에셋과 작업 기록 | 예 |
| 작업 공간 생성, 삭제, 이름 변경, 순서 변경. 캔버스 생성이나 닫기 | 예 |
| 선택/호버, 검색, 카메라, 작업 공간/캔버스 포커스, 편집/미리보기 모드, 레이아웃, 패널 펼침, 보기 옵션 | 아니요. 수동 저장은 복원 가능한 표시 상태도 함께 저장 |
| 재생/추적 컨트롤, 평가된 미리보기 프레임, 관찰 로그 | 아니요 |

저장은 하나의 완전한 버전을 담습니다. 디스크에 쓰는 동안 이루어진 내용 편집은 저장되지 않은 상태로 남으며, 표시 상태 변경은 저장 완료를 막지 않습니다. 커밋되지 않은 필드를 저장된 값으로 되돌리면 그 필드의 변경 표시가 사라집니다. 커밋된 히스토리는 여전히 저장이 필요합니다.

GUI의 버리기와 열기는 교체 경계를 잡기 전에 앞서 진행 중인 편집과 필드 제출을 기다립니다. 버리기는 이전의 저장되지 않은 내용을 교체하는 것을 허용하지만, 여는 동안 새 내용 편집이나 다른 프로젝트 불러오기가 일어나면 여전히 교체를 거부합니다. 불러오는 동안의 표시 상태 변경은 열기를 막지 않습니다. 취소하거나 실패하면 원래 프로젝트와 복구 기록이 유지됩니다. 깨끗한 프로젝트가 성공적으로 설치되면, 대기 중인 이전 복구 쓰기가 끝난 뒤 버려진 복구 표식을 지웁니다.

## 아카이브 레이아웃(v2)

저장은 v2로 씁니다. 각 히스토리 리비전은 내용 주소 방식의 문서 노드로 나뉘며, 바뀌지 않은 노드는 리비전끼리 공유합니다. 각 노드는 자체 스키마 버전을 가집니다.

| 경로 | 내용 |
| --- | --- |
| `manifest.json` | 형식, 버전 `2`, 프로젝트 UUID, SHA-256 목록 |
| `source/original.psd` 또는 `source/original.cmo3` | 가져온 원본. 소재로 만든 프로젝트는 PSD 원본을 생성 |
| `history/HEAD.json` | 현재 노드와 노드 순서 |
| `history/nodes/` | 부모로 연결된 불변 노드와 메타데이터(v1과 같음) |
| `history/revisions/<key>.json` | 리비전별: `{schema, nodes:{kind:hash}, overrides?, clips?, payloads?}` |
| `document/nodes/<kind>/<sha256>.json` | 문서 노드 `{schema, kind, value}`. 종류는 `source`(레이어와 그룹), `generation-source` / `mesh-source`(이전 빌드가 쓴 `placement-source`는 읽을 때 무시), `layers`(표시 여부, 소프트 삭제, 분류, 부모, 메시 및 텍스처 재정의), `settings`, `rig`(파라미터, 뼈대, 흔들림, 시뮬레이션, 물리, 히트 영역 등 리그 정의), `journal`(재정의를 제외한 작성 저널), `layout`(사용자 태그, 소재 연결, 생성 상태), `materials`(소재 라이브러리: 폴더와 항목. 픽셀은 `assets/`의 래스터를 참조하고 SVG 텍스트는 인라인. PSD나 CMO3에서 읽은 폴더는 `origin` 파일 이름을, 그 항목의 `placementCanvas`는 기본 배치가 놓인 캔버스 크기를 가짐), `document`(나머지 필드). `layout`과 `materials`는 레이아웃 상태가 있는 문서에만 쓰며, 이를 모르는 빌드는 그런 문서를 열지 않음 |
| `document/nodes/payload/<sha256>.json` | 큰 저널 항목을 위한 내용 주소 방식 페이로드 노드. 스키마 2 리비전이 `payloads` 아래에 나열 |
| `document/overrides/<sha256>.json` | 생성 재정의(`generated_override`)와 저널 안의 위치 |
| `document/clips/<sha256>.json` | 모션 클립(`motions`, 각 클립의 `events` 포함), 생성 모션 설정(`motionPresets`), 표정(`expressions`), 포즈(`pose`). 뒤의 둘은 프로젝트가 표정을 편집했거나 포즈 그룹을 설정한 뒤에만 |
| `document/bakes/<sha256>.bin` | 시뮬레이션 베이크(압축 JSON, 아래 「베이크 파일」 참고). 스키마 4 리비전이 `bakes` 아래에 나열 |
| `assets/` | PNG로 인코딩한 중복 제거된 RGBA 래스터 |
| `auxiliary/assets/` | 단계별 소재 메타데이터 |
| `auxiliary/views/`, `auxiliary/view-images/` | 렌더링된 뷰의 공간 참조. 이전 프로젝트에는 렌더링된 모든 이미지도 들어 있지만, 이제 저장할 때 유지하지 않음 |
| `auxiliary/workflow/` | 참조 패키지, 등록, 배치 기록 |
| `auxiliary/tasks.json` | 에이전트 작업 기록과 이벤트 |
| `workspace.json` | 지속되는 UI 레이아웃, 카메라, 선택, 파라미터 미리보기, 주석, 타임라인 보조 도구(`timelineAids`), 로그 |
| `images/<hash>.png` | 로그 이미지 |
| `rig/objects/` | 리그 객체: 체크포인트 레코드가 가리키는 것(체크포인트가 있는 리비전에 필요)과 각 리비전의 작성 리그에 속하는 것 |
| `rig/revisions/` | 선택 사항. 각 리비전의 작성 리그 인덱스(아래 「작성 리그」 참고) |
| `cache/head/` | 선택 사항. 헤드 리비전을 다시 빌드하기 위한 버려도 되는 캐시(아래 「헤드 캐시」 참고) |
| `thumbnail.png` | 선택 사항. 시작 페이지용 미리보기: 정지 상태의 저장된 모델, 긴 변 최대 256 px. 열 때는 읽지 않으며 저장할 때마다 새로 씀 |

문서 노드, 재정의, 클립 파일은 그 바이트의 SHA-256으로 이름을 붙이며, 열 때 확인합니다. 분할은 무손실입니다. 열 때 각 리비전의 완전한 문서를 인덱스로부터 결합하므로 리비전 ID, 노드 ID, 분기는 바뀌지 않습니다. 완전한 리그 모델은 저장하지 않습니다. 작성 리그가 있는 리비전은 열 때 그것으로부터 빌드하고, 그 밖의 리비전은 원본, 설정, 편집으로부터 빌드합니다. 보조 항목은 사용한 기능에 따라 달라집니다. `cache/`에는 버려도 되는 재빌드 캐시만 들어 있으며 어떤 정체성에도 참여하지 않습니다.

### 체크포인트

저널 항목 `rig_checkpoint`(`{op, v:1, authored:{header, frame, deformers, meshes}, issues}`)는 작성 리그를 저널 안의 그 위치에 데이터로 저장합니다. `authored`는 아래와 같은 작성 리그 인덱스(헤더와 객체 해시)이고, `issues`는 그것을 쓴 재생성 병합이 깔끔하게 옮기지 못한 내용(`{kind, target, detail}`. 설계: [실체화된 리그](MATERIALIZED_RIG.md))입니다. 재생은 마지막 체크포인트에서 시작합니다. 그 작성 리그(아틀라스가 바뀌었으면 캔버스 텍스처 좌표를 통해 다시 바인딩)와 그 뒤의 항목을 사용하며, 그 앞의 항목은 히스토리일 뿐 더 이상 재생하지 않습니다. 애플리케이션은 편집이 생성 결과를 바꿀 때, 생성된 모델을 처음 편집할 때, 그리고 마지막 체크포인트 뒤에 항목이 32개 쌓였을 때 체크포인트를 씁니다. 사용자가 직접 편집하지는 않습니다. 뒤의 두 경우는 편집 전의 작성 리그를 저장하고 이전 체크포인트의 `generated` 스냅샷을 이어받으므로, 이 버전이 편집하는 모든 생성 프로젝트는 리비전 3이 됩니다.

체크포인트 객체는 문서에 속합니다. 작업 저장소는 그것을 가리키는 스냅샷보다 먼저 `<project>/rig-objects/`에 쓰고, 저장하면 `rig/objects/`에 보관합니다.

### 작성 리그

`rig/revisions/`에는 각 리비전의 작성 리그가 들어 있습니다. 이는 레거시 정적 편집과 저널 전체를 적용한 뒤, 흔들림, 시뮬레이션 반영, 재정의 병합 전의 생성 기반(뼈대 베이크 포함)입니다(설계: [실체화된 리그](MATERIALIZED_RIG.md)).

| 경로 | 내용 |
| --- | --- |
| `rig/objects/<sha256>.bin` | 리그 객체 하나(`RigIrObjects`): 프레임(디포머와 메시를 제외한 전부), 디포머 하나, 또는 메시 하나. 그 바이트의 SHA-256으로 이름을 붙이며 리비전과 체크포인트끼리 공유 |
| `rig/revisions/<revision>.json` | `{header, frame, deformers:[...], meshes:[...]}`: 헤더와 리그 순서대로의 객체 해시 |

- 객체는 매직 넘버, 인코딩 버전, 객체 종류가 붙은 중립 IR의 바이너리 형태(`RigIrBinary`, 부동소수점은 비트 단위로 보존)를 씁니다. 읽기는 `RigIrObjects.MIN_VERSION` 이후의 모든 버전을 받아들이며, 새 IR 필드는 그것을 추가한 버전부터만 읽습니다. 인코딩 버전 5부터 부동소수점 배열은 바이트 평면으로 씁니다(모든 값의 첫 바이트, 그다음 모든 두 번째 바이트, …). 값은 바뀌지 않으며 DEFLATE가 훨씬 잘 압축합니다. 버전 6은 IR의 히트 영역을 추가합니다(이전 객체는 이전처럼 읽음. 이후에 저장하는 객체는 버전 6으로 쓰므로 내용이 바뀌지 않아도 새 해시를 얻으며, 업그레이드 후 첫 체크포인트를 쓸 때 아카이브가 한 번 커지고 그 뒤로는 평소대로 공유). 체크포인트가 해시로 가리키는 기존 객체는 인코딩을 유지합니다.
- 헤더 `{format:"psd2live-authored-rig", version:1, build, binding_key, pages, layers, bounds, face, warnings, skipped, visibility}`: 메시와 텍스처 페이지의 대응, 원본 레이어와 중립 경계, 얼굴 중심·반지름·초기 기울기, 생성 경고, 재생이 건너뛴 항목, 레이어 표시 여부가 적용되는 메시, 아틀라스 바인딩 키. 부동소수점은 원시 비트로 씁니다.
- 파일 이름의 리비전 키는 문서의 리비전 ID(`WorkspaceRevisions.of`)로, 빌드가 조회할 때 쓰는 키입니다.
- 바인딩 키는 생성 기반이 바인딩된 아틀라스 배치, 페이지 크기, 텍스처 레이어 사각형을 요약한 것입니다. 열 때 현재 빌드가 리비전의 아틀라스를 배치합니다. 키가 같으면 저장된 텍스처 좌표를 그대로 쓰고, 다르면(이 빌드가 다르게 배치하면) 캔버스 텍스처 좌표를 통해 새 타일로 옮깁니다. 읽을 수 없거나 체크섬이 맞지 않는 항목은 무시하며, 그 리비전은 이전처럼 빌드합니다.
- 저장은 이 프로세스가 리비전용으로 빌드한 작성 리그와 열린 아카이브에서 읽은 작성 리그를 쓰되, 헤드, 각 분기 끝, 저널에 체크포인트가 없는 리비전에 대해서만 씁니다. 그 밖의 리비전은 기반을 생성하지 않고 마지막 체크포인트에서 빌드하므로 자기 사본을 더 이상 유지하지 않습니다(유지하면 바뀐 메시마다 아카이브에 객체가 하나씩 늘어남). 그 밖의 리비전에는 작성 리그가 없습니다. `-Dpsd2live.materializedRigs=false`로 읽기와 쓰기를 끕니다.
- 리비전 인덱스는 어떤 리비전 ID나 문서 노드에도 포함되지 않으며, 인덱스가 없는 리비전은 이전처럼 빌드합니다. 저널에 체크포인트가 있으면 마지막 체크포인트에서, 없으면 생성과 재생으로 빌드합니다. 가져온 CMO3 모델은 작성 리그를 쓰지 않습니다.

### 헤드 캐시

저장 시 `cache/head/`를 쓸 수 있습니다. 헤드 리비전을 다시 빌드할 때 드는 비싼 중간 결과 중 재사용해도 안전한 것을 담아, 열 때 다시 계산하지 않아도 되게 합니다. 권위 있는 데이터가 아닙니다. 열 때는 여전히 원본, 설정, 저널로부터 완전히 다시 빌드하며, 캐시는 메모리의 생성기 캐시를 미리 채울 뿐입니다. 항목을 쓸지는 그 캐시 자체의 내용 키가 결정하므로, 캐시가 있든 없든 다시 빌드한 모델은 비트 단위로 같습니다.

| 경로 | 내용 |
| --- | --- |
| `cache/head/manifest.json` | `{format:"psd2live-head-cache", version:1, build, generator, revision, language, entries:[{kind, file, sha256, bytes}]}` |
| `cache/head/skeleton-bake.bin` | 헤드의 뼈대 베이크: JSON 헤더(베이크 버전, 캐시 키, 뼈대 정의, 읽기 집합, 읽지 않은 객체의 부모 재지정, 선택적 전체 해시) 뒤에 출력 모델을 바이너리 IR(`RigIrBinary`, 부동소수점은 비트 단위로 보존. 아틀라스, 원본 목록, 변형 경로는 제외하며, 적중하면 새 기반 리그에서 가져옴)로 씀 |

- 키: 헤드 리비전 ID, 애플리케이션 버전(`Compiler.version`), 생성기 상수 `ProjectHeadCache.GENERATOR`(항목 자체의 키가 놓칠 수 있는 방식으로 생성이 바뀌면 올림), 인터페이스 언어. 하나라도 다르면 캐시 전체를 버립니다. 그다음 항목 안의 뼈대 캐시 키(`SkeletonRig.BAKE_VERSION`, 베이크가 읽는 모든 것, 언어 포함)가 적중 여부를 결정합니다.
- 뼈대 베이크만 캐시합니다(콜드 약 5–7초, 적중 시 1–7 ms). 64 MB를 넘는 항목은 쓰지 않습니다. 저장은 프로세스에서 가장 최근에 사용한 베이크 중 뼈대 정의가 헤드와 같은 것을 가져가며, 없으면 캐시를 쓰지 않습니다. `-Dpsd2live.headCache=false`로 쓰기와 읽기를 끕니다.
- 열 때 매니페스트 형식, 키, 항목 체크섬이 맞지 않거나 항목이 없거나 잘렸거나 디코딩할 수 없으면 로그에 남기고 버리며, 열기를 실패시키지 않습니다. 읽은 뒤 압축을 푼 디렉터리에서 `cache/`를 제거합니다.
- 캐시는 `history/`와 `document/` 밖에 있으며 어떤 리비전 ID, 문서 노드, 히스토리에도 포함되지 않습니다. 캐시가 없는 아카이브는 이전처럼 열립니다. 아카이브 매니페스트는 다른 파일과 마찬가지로 캐시 파일을 나열하고 검증합니다. 이전 v2 빌드는 나머지와 함께 압축을 풀지만 읽지 않으므로 이런 아카이브도 열 수 있으며, 다음 저장 때 그 폴더를 버립니다.

### 노드 스키마

노드나 리비전 인덱스는 더 새로운 필드를 쓸 때만 더 새로운 스키마로 넘어갑니다. 그 밖의 모든 노드는 여전히 바이트 단위로 스키마 1로 쓰므로, 이전 프로젝트는 이전과 같은 노드 해시와 리비전 인덱스로 저장됩니다.

| 스키마 | 적용 대상 | 새 필드 |
| --- | --- | --- |
| 노드 1 | 아래 필드가 없는 노드 | — |
| 노드 2 | 레이어 `rect`가 있는 `source` 또는 추가 원본 소재 노드, `textureOverrides`가 있는 `layers`, `atlas`나 `atlasArrangement`가 있는 `settings` | 아래 텍스처 필드 참고 |
| 노드 3 | 레이어 `transform`이 있는 `source` 또는 추가 원본 소재 노드 | 레이어 전체 변환 `[a, b, c, d, e, f]`(`x' = a·x + c·y + e`, `y' = b·x + d·y + f`, 캔버스 단위, y 아래쪽). 레이어의 프레임(정수 경계와 `rect`)에 적용. 텍스처 좌표는 프레임에 고정되며 생성은 프레임만 읽음. 항등 변환은 쓰지 않음 |
| 노드 4 | 레이아웃 노드 도입 후 추가된 필드가 있는 `layout` / `materials` 노드 | 참조 이미지, 참조 레이어와 핀, 드로잉, 소재의 캔버스와 참조 표시 |
| 노드 5 | `expressions`나 `pose`가 있는 `clips` 노드, 또는 `events`가 있는 모션 클립 | 표정 `{id, name, fade_in, fade_out, entries:[{parameter, blend, value}]}`(`blend`는 `ADD` / `MULTIPLY` / `OVERWRITE`), 포즈 `{fade_in, groups:[[{part, links?}]]}`, 이벤트 `[{time, value}]` |
| 노드 5 | `hitAreas`가 있는 `rig` 노드 | 테스트 순서대로의 히트 영역 `{id, name, meshes}`. [내보내기 대상](EXPORT_TARGETS.md#히트-영역) 참고 |
| 노드 6 | `modifierStack`이 있는 `rig` 노드 | 명시적이고 순서 있는 모디파이어 인스턴스, 알고리즘 버전, 고정된 대상, 설정, 휴면 오버라이드, 퇴역한 인스턴스 ID, 적용된 기능. 필드가 없으면 레거시 프리셋 흐름을 유지하고, 빈 스택이면 프리셋을 추가하지 않습니다 |
| 노드 6 | `file`이 있는 모션을 가진 `clips` 노드 | 적용된 모션이 유지하는 안정적인 에셋 이름. 표시 이름이 바뀌어도 변하지 않습니다 |
| 노드 7 | `captured_ranges`가 있는 모션을 가진 `clips` 노드 | 곡선과 함께 고정한 파라미터 범위 `{min, max, repeat}`. 재구성할 때 원래 제어점이 바뀌지 않게 합니다 |
| 리비전 1 | 저널이 페이로드 노드를 가리키지 않음 | — |
| 리비전 2 | 저널이 페이로드 노드를 가리키며 `payloads` 아래에 나열 | `{"$payload": "<sha256>"}` 저널 항목 |
| 리비전 3 | 저널에 `rig_checkpoint` 레코드가 있음 | 인덱스가 그것이 가리키는 리그 객체를 `rig` 아래에 나열하며, 객체는 아카이브의 `rig/objects/`에 보관. `payloads`도 나열할 수 있음 |
| 리비전 4 | 시뮬레이션에 베이크가 있음 | `rig` 노드가 각 베이크를 `{"$bake": "<sha256>"}`로 쓰고, 인덱스가 `bakes` 아래에 나열하며, 내용은 `document/bakes/`에 있음. `payloads`와 `rig`도 나열할 수 있음 |

스키마 1만 읽는 빌드는 새 필드를 버리지 않고 스키마 2 노드나 리비전을 거부합니다. 이 빌드는 노드 스키마 1–4(`settings` 노드는 1–5, `rig` 노드는 1–6, `clips` 노드는 1–7)와 리비전 스키마 1–4를 읽으며, 그보다 높은 것은 여전히 거부합니다. 스키마 5를 모르는 빌드는 표정, 포즈, 모션 이벤트가 있는 `clips` 노드를 버리지 않고 거부합니다. 스키마 4 `rig` 노드는 인덱스가 나열한 베이크만 가리킬 수 있으며, 열 때 모든 베이크 파일을 해시와 대조합니다. 이전 빌드는 리비전 스키마 4를 거부하므로, 베이크가 있는 프로젝트는 한 번 저장하면 이전 빌드에서 더 이상 열리지 않습니다. 스키마 3 인덱스는 `rig`를 나열해야 합니다. 열 때 `rig/objects/`에 나열된 모든 객체가 있는지 확인하며, 하나라도 없으면 아카이브를 거부합니다. 스키마 3이 없는 빌드는 그런 리비전을 빌드할 수 없으므로 거부합니다. 스키마 2 리비전은 페이로드를 하나 이상 나열하며, 그 저널은 나열한 페이로드만 가리킬 수 있습니다. 저장할 때 이미 스키마 2 노드가 있는 리비전은 512자 이상인 작성 저널 항목을 페이로드 노드로 옮기고(저널 노드 안의 참조는 80자 미만), 각 페이로드를 한 번만 쓰며, 스키마 2 인덱스를 받습니다. 스키마 1만 읽는 빌드는 어차피 그런 리비전을 열 수 없습니다. 새 필드가 없는 문서는 여전히 스키마 1만 쓰며, 노드와 인덱스는 바이트 단위로 같습니다. 긴 히스토리의 각 리비전이 더 이상 저널 전체를 저장하지 않으므로, 아카이브 크기와 저장 시간이 리비전 수의 제곱에 비례해 늘어나지 않습니다.

### 베이크 파일

시뮬레이션 베이크(`rigEdits.simulations[*].bake`)는 대부분 정점 오프셋 배열로, 흔히 리비전 문서의 대부분을 차지하며 여러 리비전에 걸쳐 바뀌지 않습니다. 베이크는 `rig` 노드에 두지 않습니다. 서로 다른 베이크마다 그 바이트의 SHA-256으로 이름을 붙인 압축 JSON 파일 하나로 저장하고 리비전끼리 공유하므로, 뼈대나 다른 리그 정의를 바꿔도 더 이상 베이크가 복사되지 않습니다.

압축 JSON(`PackedJson`)은 JSON 값을 무손실로 저장합니다. 요소가 8개 이상이고 모든 숫자가 그 float32 값 자체의 텍스트(프로그램이 float를 쓰는 방식)와 정확히 같게 쓰인 배열은 JSON 텍스트에서 `{"$f32": index}`로 바뀌고, 그 숫자들은 텍스트 뒤에 원시 비트로 들어갑니다. 그 밖의 숫자는 텍스트를 유지하므로 디코딩하면 요소 단위로 같은 JSON이 돌아옵니다. 레이아웃: 매직 `P2LJ`, 버전 1, 플래그(1: 텍스트에 참조가 없음. 값 자체에 `{"$f32": …}` 객체가 있을 때 사용), 텍스트 길이와 UTF-8 바이트, 배열 수, 그다음 각 배열의 길이와 바이트 평면으로 쓴 float(모든 float의 첫 바이트, 그다음 모든 두 번째 바이트, …. DEFLATE가 잘 압축함). 정수는 빅 엔디언입니다.

### 텍스처 필드

네 가지 모두 선택 사항입니다. 없으면 이전 동작을 따르며 이전 리비전을 유지합니다. 생성과 아틀라스 배치가 이를 읽습니다(규칙은 [문서 계층](DOCUMENT_LAYER.md#레이어별-크기) 참고).

- 원본 레이어 `rect: [left, top, width, height]`: 캔버스 단위의 부동소수점 캔버스 사각형으로, 레이어가 캔버스에서 놓인 위치이며 픽셀 작업으로는 절대 바뀌지 않습니다. 없거나 정수 경계와 같으면 생략합니다. 정수 경계는 둘러싸는 상자로 남으며 사각형을 포함해야 합니다. 레이어 래스터의 해상도는 자유이며, 사각형 크기 대비 래스터 픽셀이 레이어 고유의 밀도로, 축마다 다를 수 있습니다.
- 문서 `textureOverrides: {layer ID: {density?, lock?, pin?: {page, x, y}}}`: 레이어별 텍스처 밀도 배율(기본값 1, 래스터 자체의 해상도), 잠금(아틀라스를 줄여야 할 때도 밀도를 유지), 고정 아틀라스 위치(페이지와 페이지 왼쪽 위 픽셀). 모두 기본값인 항목은 쓰지 않습니다. `layers` 노드에 저장합니다.
- 설정 `atlas: {pageSize, maxPages, padding}`: 아틀라스 예산. 없으면 예산은 레거시 `atlasSize` / `texturePadding`이며 기본 8페이지입니다. 빠진 멤버도 같은 방식으로 대체됩니다.
- 설정 `atlasArrangement: {fitStep, tiles: {layer ID: {page, x, y, rotation?, footprint?: {cell, columns, rows, bits}}}}`: 저장된 아틀라스 배치. `x`, `y`는 타일의 똑바른 사각형의 왼쪽 위이며, `rotation`(도 단위, 없으면 0)은 Umamo의 배치가 회전하는 방식(y 아래쪽 기준 시계 방향)으로 중심을 기준으로 회전합니다. 없으면 빌드할 때마다 아틀라스를 자동 배치하고(이전 동작), 있으면 모든 타일이 자리를 유지하고 잠기지 않은 모든 타일이 공통 배율 `fitStep / 4096`을 따릅니다. `footprint`는 메시가 덮는 레이어 래스터의 셀입니다(각 셀은 `cell` 래스터 픽셀, `bits`는 Base64 `BitSet`인 행 우선 비트맵). 이것이 있는 타일은 그 셀만 씁니다. 새로 가져온 프로젝트는 첫 배치를 저장합니다.

## v1 호환과 마이그레이션

v1 아카이브도 여전히 열립니다. v1은 각 리비전을 하나의 완전한 스냅샷으로 저장합니다.

| 경로 | 내용 |
| --- | --- |
| `workspace/<projectId>/HEAD.json`, `history/nodes/` | 현재 노드, 노드 순서, 노드 메타데이터 |
| `workspace/<projectId>/history/snapshots/` | 각 리비전의 완전한 문서: 원본 레이어, 설정, 구조, 편집 오버레이 |
| `workspace/<projectId>/blobs/` | 중복 제거된 RGBA 래스터(PNG) |
| `workspace/<projectId>/assets/`, `views/`, `view-images/`, `workflow/`, `tasks.json` | 보조 데이터 |

나머지 항목(`manifest.json`, `source/`, `workspace.json`, `images/`)은 v2와 같습니다. v1 파일을 열면 그 스냅샷을 v2와 같은 메모리 내 문서로 바로 읽습니다. 다음 저장은 v2를 쓰며, 파일을 교체하기 전에 v1 원본을 `<name>.v1.psd2live`로 옆에 남깁니다(기존 백업은 덮어쓰지 않음). 마이그레이션은 저장 레이아웃만 바꾸며, 모든 리비전, 분기, 주석, 에셋, 뷰, 작업 기록이 유지됩니다. 작업 디렉터리는 내부적으로 스냅샷 레이아웃을 유지합니다. 열 때는 아카이브를 스냅샷으로 풀지만, 저장할 때는 스냅샷을 쓰지 않고 메모리의 히스토리를 스테이징 디렉터리에서 바로 v2 노드로 나눕니다.

작업 디렉터리 스냅샷은 공유 내용에서만 v1과 다릅니다. 새로 쓰는 스냅샷은 비어 있지 않은 `rigEdits.authoringJournal`을 `{count, chunks:[key...]}`로 저장하고, 항목은 `history/journal/<key>.json`의 내용 정의 청크에 넣습니다(청크는 다이제스트가 선택한 항목 뒤에서 끝나며 평균 약 4개 항목, 최대 16개 항목 또는 약 64K자. 키는 항목들의 SHA-256 다이제스트에 대한 SHA-256). 64K자 이상인 `rigEdits.importedCmo3`는 `{payload: sha256}`가 되고 텍스트는 `history/payloads/<sha256>.txt`에 들어갑니다. 시뮬레이션 베이크는 `{"$bake": sha256}`가 되고 내용은 `history/bakes/<sha256>.bin`에 들어갑니다(아카이브와 같은 압축 JSON. 베이크 하나는 모든 리비전에 대해 한 번만 읽히고 하나의 객체로 디코딩됨). 항목을 덧붙이면 끝 청크만 추가되며, 닫힌 청크는 리비전끼리 공유합니다. 읽을 때는 키를 확인하고 원래 스냅샷을 키 순서까지 복원합니다. v2로 묶을 때도 먼저 복원하므로 아카이브 노드는 영향을 받지 않습니다. 스냅샷은 압축된 형태의 JSON으로 씁니다. 청크를 지원하지 않는 빌드는 저널을 버리지 않고 객체 형태에서 실패합니다. v2 압축 해제도 이 공유 형태로 스냅샷을 쓰며, 읽을 때는 각 항목을 한 번만 파싱해 모든 리비전에 같은 객체를 줍니다(공유 청크 이상으로: 저널의 마지막 청크는 저널 끝에서 끝나므로, 이웃 리비전의 끝 항목은 내용으로 합쳐짐). 이전 빌드가 쓴 통째 스냅샷도 여전히 읽히며 두 형태가 공존할 수 있습니다.

내부 파일 이름은 표시 이름 대신 논리 ID의 해시를 쓸 수 있습니다. PNG 리소스는 투명 알파 아래의 RGB를 유지합니다. 리비전끼리 래스터를 공유합니다.

## 저장과 복구

PSD / CMO3 가져오기는 먼저 원본 바이트를 작업 공간의 `sources/<sha256>.<format>`에 복사하고, 그 소유한 사본을 파싱합니다. 외부 경로는 출처 정보일 뿐이며, 원본을 옮기거나 삭제하거나 바꿔도 저장을 막지 않습니다. `workspace.json`은 `originalSource: {format, sha256}`로 사본을 설명합니다. 저장은 다이제스트를 검증하고, 아카이브를 열 때는 원본을 검증하고 채택합니다. 이 설명자가 없는 이전 프로젝트도 읽을 수 있습니다. 이미지로 만든 프로젝트나 원본이 없는 프로젝트는 루트 히스토리 소재로 PSD를 생성하며, 가져온 CMO3 모델은 문서 페이로드를 유지합니다.

자동 복구는 작업 디렉터리의 `recovery.json`(스키마 `version: 1`, 아카이브 v2는 바꾸지 않음)을 사용합니다. 불러오기 정체성, Runtime 상태, 히스토리 HEAD, 지속되는 보조 데이터, 작업 공간 표시 상태, 작업 기록이 들어 있습니다. 먼저 히스토리와 참조된 리소스를 쓰고, 그다음 체크포인트를 원자적으로 교체한 뒤, 세션 포인터를 업데이트합니다. 보조 데이터만 바꾸는 포즈, 스냅샷, 주석, 표시 여부, 작업 공간 내용 편집도 복구를 예약하며, 평가된 프레임과 표시 상태만의 변경은 예약하지 않습니다. 복구는 체크포인트 HEAD를 체크아웃하고 그 내용을 복원하며, 저장되지 않은 상태로 둡니다. 체크포인트가 없는 이전 디렉터리는 히스토리만의 복구를 유지합니다. 작업 기록은 실행을 자동으로 다시 시작하지 않습니다.

백그라운드 쓰기는 대상별로 지속된 버전을 확인합니다. 대기 중인 완전한 스냅샷은 합쳐질 수 있으며, 이전 영수증은 그것을 포함하는 완전한 버전으로 확인됩니다. 실패는 그 대상에서 재시도가 성공할 때까지 그 대상에 붙어 있습니다. 저장은 프로젝트의 핵심 영수증을 기다리므로, 관련 없는 관찰 쓰기가 복구 실패를 가릴 수 없습니다. 저장하거나 버린 뒤의 정상 종료는 대기열을 비우고, 해당 복구 포인터를 제거하며, 소유한 압축 해제 디렉터리를 해제합니다. 비정상 종료는 복구 리소스를 보존합니다. 대기열 비우기가 시간 초과되면 등록을 유지합니다. 시작할 때는 살아 있는 프로세스나 복구 참조가 없는 등록된 임시 디렉터리만 회수합니다.

저장은 불변 상태를 잡아 쓰기를 직렬화합니다. 라이터는 대상 옆에 임시 아카이브를 만들고 검증한 뒤 대상을 원자적으로 교체합니다. 원자적 교체를 지원하지 않으면 실패하고 이전 프로젝트를 유지합니다. 앞선 캡처가 완료된 뒤의 편집은 저장되지 않은 상태로 남습니다.

저장은 이미 있는 것을 다시 인코딩하지 않습니다. 작업 디렉터리에 있는 래스터 PNG는 픽셀에서 인코딩하지 않고 스테이징 디렉터리로 하드 링크합니다(링크를 쓸 수 없으면 수정 시각을 유지해 복사). 리비전 분할도 한 번만 합니다. 작업 디렉터리의 `archive/` 미러는 저장하거나 연 모든 리비전의 v2 인덱스(`archive/revisions/<snapshot key>.json`: `{version, index, rasters}`)와 그것이 가리키는 문서 노드(`archive/document/`)를 유지합니다. 저장은 그 파일들을 링크하고 새 리비전만 인코딩, 분할, 해시하므로, 다시 저장하는 시간은 히스토리 길이가 아니라 바뀐 양에 비례합니다. v2 아카이브를 열면 현재 규칙으로 분할된 리비전(인라인 베이크 없음, 스키마 2 노드라면 긴 저널 항목이 이미 페이로드)을 노드와 함께 미러로 옮기므로, 열고 나서 첫 저장도 새 리비전만 처리합니다. 그 밖의 리비전은 저장할 때 다시 분할합니다. 다른 버전의 미러 레코드나 파일이 빠진 미러 레코드는 이전처럼 분할합니다. 아카이브를 쓸 때 `document/` 아래의 모든 항목을 이름이 나타내는 SHA-256과 대조하므로, 손상된 미러 파일은 잘못된 아카이브를 쓰는 대신 저장을 실패시킵니다. 아카이브를 쓸 때 각 파일을 한 번만 읽으며, 쓰는 동안 SHA-256과 CRC-32를 구하고 그것으로 매니페스트를 만듭니다. `STORED` 항목의 다이제스트는 항목 이름, 길이, 수정 시각을 키로 프로세스 안에 캐시하므로(프로젝트를 열 때도 기록), 바뀌지 않은 래스터를 다시 저장하면 해시하지 않고 복사합니다. 임시 파일을 쓰고 `fsync`한 뒤에는 스트림으로 다시 읽습니다. 항목 집합은 정확히 쓴 항목과 매니페스트여야 하고, 각 항목의 길이와 CRC가 쓴 것과 일치해야 하며, 매니페스트 바이트가 같아야 합니다. 아카이브를 디스크에 다시 풀어 해시하지는 않습니다. 오래된 캐시가 잘못된 아카이브를 만들 수는 없습니다. `STORED` 항목의 바이트는 쓰는 동안 CRC와 길이로 확인하고 다시 읽을 때 한 번 더 확인하며, 불일치가 있으면 저장을 실패시키고 기존 파일을 유지합니다. 열 때는 여전히 모든 SHA-256을 검증합니다.

열 때는 헤드 리비전만 읽고 디코딩합니다. 그 밖의 리비전은 처음 사용할 때(체크아웃, 관찰, 그 내용이 필요한 저장) 읽으며, 하나의 작업 디렉터리에서 읽은 리비전끼리 저널 항목, 베이크, 래스터를 공유합니다. v2 아카이브를 열 때 현재 규칙으로 분할된 리비전은 작업 스냅샷을 받지 않고, 처음 사용할 때 미러의 노드로부터 결합합니다(모든 노드, 항목, 리그 객체 참조는 압축을 풀 때 확인함). 저장은 아직 읽지 않은 리비전을 디코딩하지 않습니다. 미러 인덱스가 그 체크포인트의 리그 객체를 나열하고, 작성 리그는 노드의 리비전 ID로 찾습니다. 히스토리의 서로 다른 래스터는 각각 한 번만 디코딩하며, 한 리비전의 래스터는 여러 스레드에서 디코딩합니다(코어 수와 힙에 따라 제한). 작업 디렉터리가 쓰는 8비트, 비인터레이스 RGBA/RGB PNG는 RGBA 바이트로 바로 디코딩하고, 그 밖의 PNG는 ImageIO로 읽습니다. 어느 쪽이든 결과를 래스터 다이제스트와 대조하며, 확인된 다이제스트로 리비전과 리그 단계 캐시를 미리 채워 다시 계산하지 않습니다. 에셋 카탈로그 확인은 에셋 메타데이터를 읽고 픽셀을 디코딩하지 않은 채 각 래스터 파일이 있는지 확인하며(픽셀은 에셋을 불러올 때 확인), 열 때마다 한 번 합니다.

일반 저장은 내용이 HEAD와 이미 같으면 히스토리 노드를 추가하지 않습니다. 명시적 체크포인트는 바뀌지 않은 내용도 기록할 수 있습니다. 실패한 저장은 지속된 완료가 아니므로 오류 상태를 확인하세요.

모든 분기를 유지합니다. 실행 취소는 부모를 따르고, 다시 실행은 후속 노드를 선택하며, 오래된 노드에서 편집하면 분기가 생깁니다. 분기의 이름 변경, 주석 추가, 숨기기는 원래 노드를 다시 쓰거나 에셋을 제거하지 않습니다.

새 파라미터의 생성, 업데이트, 삭제는 `rigEdits.authoringJournal`에 저장되며 편집 순서대로 재생됩니다. 따라서 삭제는 앞선 키폼과 마지막 기본값 업데이트 뒤에 실행됩니다. 레거시 정적 파라미터 재정의는 원래 재생 순서를 유지하며, 기존 스냅샷, 리비전, 노드 ID는 다시 쓰지 않습니다. 채널 키폼은 기하 편집과 함께 유지됩니다.

내부 `canvas_mesh_rebuild` 저널 레코드는 부모 로컬 정점, 삼각형, 원본 캔버스 픽셀 단위의 텍스처 좌표, 이전 정점 보간 원본, Glue 정점 매핑을 저장합니다. 선택적 `neutral_bounds`는 교체 메시의 중립 캔버스 경계를 기록합니다. 가져온 CMO3 캔버스 기반을 처음 교체할 때는 `previous_parent_points`를 포함할 수 있습니다. 재생은 보간 전에 일반 폼과 블렌드 폼을 그 중립 부모 좌표로 다시 기준을 잡고, 경로는 원래 삼각형을 통해 변환합니다. 재생은 이전 기하의 SHA-256, 부모, 소재 정체성을 확인하고(기반 생성이 기록된 부모를 더 이상 만들지 않으면, 예를 들어 뼈대를 켠 뒤의 팔 늘어뜨림 Warp처럼, 정점 수만 확인하고 기록된 점을 캔버스 텍스처 좌표에 아핀 피팅해 현재 부모의 공간으로 옮김. [DOCUMENT_LAYER](DOCUMENT_LAYER.md#더-이상-생성되지-않는-부모) 참고), 현재 아틀라스에 맞춰 UV를 재구성하며, 키폼, 블렌드 셰이프, 경로, 정점 그룹, Glue를 마이그레이션합니다. 메시만의 설정 변경은 앞선 저널과 생성 레코드를 유지하고, 히스토리를 다시 쓰지 않고 교체 레코드를 덧붙입니다. 아카이브 형식 버전은 바뀌지 않습니다.

내부 `canvas_mesh_create` 레코드는 원래 생성 입력에 없던 메시를 담습니다: 안정적인 ID, 원본과 레이어 정체성, 투명 커버리지 경계, 부모와 파츠, 정적 재질, 로컬 정점/삼각형, 캔버스 텍스처 좌표, 생성된 파라미터/키폼/채널, 경로. 재생은 현재 아틀라스를 해석하고, 사용되지 않은 메시 ID(`replace: true`인 레코드는 그 ID의 메시를 그리기 목록과 파츠 위치를 유지한 채 교체하며, 없으면 생성함. 가져온 이미지를 배치할 때 체크포인트된 리그에 이미 그 메시가 있으면 이 레코드를 씀)와 기존 부모 및 소재를 요구하며, 기하, 키폼, 래스터 크기를 검증합니다. 일반 투명 레이어나 입에 처음으로 보이는 페인트를 하면 메시가 자동으로 생성되며, 이후 지워도 기하와 바인딩은 유지됩니다. 메시 설정은 현재 후보에서 생성 기하를 업데이트하고 다시 바인딩된 경로와 가중치를 유지하며, 이전 히스토리 스냅샷은 불변으로 남습니다. 아카이브 형식 버전은 바뀌지 않습니다.

이전 내부 `canvas_source_partition` 레코드(현재는 가져온 CMO3 모델에만 씀)는 원본 메시 정체성, 로컬 기하 지문, 부모, 원래 정점 소유 관계, 그리고 각 조각의 메시/레이어 정체성, 이름, 표시 여부, 로컬 기하, 캔버스 텍스처 좌표, 정점 계보를 저장합니다. 재생은 원래 저널 위치에서 바인딩을 복사하고 현재 아틀라스를 해석하며, 삭제된 원본 메시는 그 뒤에 걸러냅니다. 컴포넌트 Glue는 쌍 순서를 유지합니다. 시뮬레이션 대상, 실체화된 오프셋, Glue 역할은 같은 문서 후보 안에서 마이그레이션됩니다. 투명한 생성 자리 표시자는 중복 메시를 만들지 않고 텍스처 커버리지를 유지합니다. 히스토리 노드와 아카이브 형식 버전은 바뀌지 않습니다.

내부 `art_primitive` 레코드는 생성된 모델의 다각형, 컴포넌트, 앞뒤 깊이 분할을 기록합니다. 저널 위치에서 `supersedes`에 나열된 메시를 제거하고 그 자리를 파츠가 대신합니다. 원래 레이어는 `source`에서 빠지고 고정된 `generationSource`에만 남으며, `deletedLayerIds`에 추가되지 않고, 파츠는 일반 원본 레이어가 됩니다. 분할은 재생성입니다. 생성기가 원래 메시를 만들었다면 레코드는 버전 2(`v: 2`)이며, 생성기가 파츠를 무엇으로부터 빌드하는지(정지 캔버스 메시, 레이어와 분류, 빈 `authored` 객체)만 선언하고, 사용자가 원본에 가한 변경은 3방향 병합으로 파츠에 옮겨집니다. 그렇지 않다면(저널이 만든 메시) 레코드는 버전 1이며 파츠가 모든 데이터를 사용자 자신의 객체로 가집니다. 어느 쪽이든 레코드 뒤에 `rig_checkpoint`가 오며, 레코드는 재생되지 않습니다. 필드와 생성 입력의 처리는 [문서 계층](DOCUMENT_LAYER.md#분할-실체화-아트-프리미티브-레코드-art_primitive) 페이지에 설명되어 있습니다.

이전 버전이 쓴 레코드도 여전히 읽힙니다. 버전 1 레코드는 파츠를 통째로 담고, 버전 2 레코드는 생성된 것과 다른 재질 필드와 사용자 데이터를 `authored`에 담으며, 레코드 바로 뒤에 `geometry_residual` / `channels_residual`과 `generated_override` 항목이 옵니다. 뒤에 체크포인트가 없으면 이전처럼 재생됩니다. 그런 프로젝트를 처음 편집하면 저널이 끝난 곳에서 현재 작성 리그를 체크포인트로 저장하며, 그 뒤로는 그 레코드들을 재생하지 않습니다. 이전 프로젝트의 `canvas_source_partition`과 `canvas_depth_split`도 같은 방식으로 처리하며, 아카이브 형식 버전은 바뀌지 않습니다.

내부 `mesh_generation_baseline` 표식은 기반 생성에 쓰인 앞선 전역 메시 설정, 레이어별 재정의, 알파 임계값을 유지합니다. 요청된 재생성에서는 현재 문서 설정이 기준입니다. 이후의 레이어/전역 업데이트와 초기화는 저장된 메시 입력이나 현재 픽셀로부터 재생성하고, 실제 중립 부모를 통해 변환하며, 순서가 있는 `canvas_mesh_rebuild` 레코드를 덧붙입니다. 일반, 분할, 생성, 가져온 CMO3 메시가 이 교체 경로를 공유합니다. 일반/블렌드 폼, 경로, 정점 그룹, Glue, 시뮬레이션 오프셋은 새 토폴로지로 마이그레이션됩니다. 베이크는 정점 수를 업데이트하되 원래 지문과 품질 지표를 유지하므로, 오래된 입력 진단이 정직하게 유지됩니다. 숨겨진 메시는 걸러내기 전에 재생성되며, 복원할 때 교체된 토폴로지를 씁니다. 이전 문서는 실제 메시 변경 뒤의 새 후보에서만 이 표식을 얻으며, 이전 리비전, 히스토리 노드, 아카이브 버전은 바뀌지 않습니다. 가져온 모델은 교체된 텍스처 주소만 정규화합니다. 완전히 투명한 소재는 작성된 토폴로지를 유지합니다. 각 교체는 앞선 토폴로지의 오프셋을 보간하므로, 메시를 거칠게 만든 뒤 설정을 초기화해도 버려진 고주파 디테일은 되살아나지 않습니다.

소프트 삭제는 문서의 기존 `deletedLayerIds`를 사용하며, 원본 픽셀, 순서가 있는 작성 기록, 앞선 불변 히스토리 노드를 유지합니다. 생성 레코드, 깊이 분할, 내부 `layer_membership` 표식이 있는 프로젝트는 전체 입력을 다시 빌드하고 재생한 뒤, 활성 미리보기나 내보내기에서 삭제된 레이어와 파생된 입술을 걸러내고 마스크 참조, Glue, 경로, 정점 그룹을 제거합니다. 복원은 저장된 ID와 바인딩을 재생합니다. 일반 프로젝트에서 처음으로 실제 삭제나 복원을 하면 새 후보에서 현재 생성 범위와 모든 원본/Drawable 정체성을 고정하고, `op`만 담은 `layer_membership` 표식을 추가합니다. 복원은 이 정체성 기준을 유지합니다. 가져온 CMO3 모델은 원래 ID와 좌표 프레임을 유지하고 표식만 추가합니다. 이 레코드가 없는 이전 문서는 자동 업그레이드나 리비전·노드 재작성 없이 원래 생성 규칙을 유지합니다. 삭제 중에 바뀐 메시 설정도 숨겨진 메시를 재생성하고 다시 바인딩된 경로와 가중치를 유지하며, 아틀라스 제약은 전체 입력을 사용합니다. GUI와 MCP의 삭제, 선택/전체 복원은 후보 커밋을 공유하며, 반복된 작업은 히스토리를 추가하지 않습니다. 기존 저널과 기준 필드를 사용하며, 아카이브 형식 버전은 바뀌지 않습니다.

히스토리 문서의 선택적 `generationSource`는 현재 소재와 같은 캔버스, 레이어, 래스터 블롭 인코딩을 사용합니다. `source`가 칠한 픽셀을 제공하는 동안, 기반 리그 생성에 쓰인 원래 래스터 형태를 유지합니다. 미리보기와 내보내기는 같은 기하를 생성하고, 원본 캔버스 좌표를 통해 UV를 다시 매핑하며, 더 좁게 잘라낸 뒤에는 투명 커버리지를 채워 유지된 메시가 이웃 타일을 샘플링하지 않게 합니다. 선택적 `meshSource`는 같은 인코딩을 사용하며, 명시적으로 다시 빌드했거나 처음 만든 레이어의 입력을 업데이트하여, 메시를 유지하는 이후 페인트 중에도 생성된 입술 윤곽과 색을 보존합니다. 생성 입력이 고정된 뒤에 추가된 레이어(에이전트가 추가한 이미지 등)는 생성 입력에 없으며 현재 픽셀로부터 생성합니다. 그런 레이어를 처음 칠하거나 이미지를 교체하면, 메시 윤곽을 추적하는 방식대로 이전 픽셀을 먼저 `generationSource`에 고정합니다. `meshTrace = CANVAS`에서는 캔버스 해상도로(정수 경계에서 캔버스 단위당 1픽셀), `TEXTURE`에서는 정수 경계에서 고유 밀도의 텍스처로(부동소수점 사각형을 래스터에 접어 넣음) 고정하므로, 메시를 유지하는 페인트는 토폴로지를 유지하고 다시 빌드할 때는 원래 메시에서 마이그레이션합니다. 깊이 분할 앞면, 아트 프리미티브 파츠, 분할 조각은 자체 레코드를 유지합니다. 에셋 레이어를 다시 배치하면 항목을 버리므로 메시가 새 배치를 따릅니다. 기존 리비전은 소급해 채우지 않습니다. 생성된 텍스처 입력을 업데이트하는 것은 정점이 그대로여도 지속되는 변경입니다. 선택적 `placementSource`는 같은 원본 인코딩을 사용해 파일에서 가져온 이미지의 잘라낸 픽셀을 유지하고 그런 레이어를 식별합니다. 가져오기와 배치는 더 이상 픽셀을 리샘플링하지 않고 레이어의 캔버스 사각형(`rect`)만 바꿉니다. 이전 버전이 경계에 맞춰 크기를 바꾼 레이어는 다시 배치하면 이 픽셀로 돌아갑니다. 네 가지 원본과 히스토리 노드는 모두 중복 제거된 PNG 블롭을 공유합니다. 새 필드를 생략하면 기존 리비전과 노드 정체성이 보존됩니다.

GUI에서 캡처한 픽셀과 MCP 래스터 제스처는 같은 문서 후보를 준비합니다. 모든 픽셀을 지워도, 메시 재빌드를 요청하더라도 레이어, 기반 메시, 작성된 바인딩은 유지됩니다. CMO3 페인트는 관련 없는 메시의 원래 아틀라스와 UV를 유지하고, 수정된 메시에 대해서만 칠한 텍스처 페이지를 추가합니다.

다시 열면 리비전에 저장된 작성 리그나 저널의 마지막 체크포인트로부터 모델을 빌드하며, 둘 다 없으면 원본, 설정, 재생 가능한 편집으로부터 다시 빌드합니다. 네이티브 핸들, 연결, 실행 중인 작업, 애니메이션 시계는 직렬화하지 않습니다. 에이전트 작업 기록은 실행을 자동으로 다시 시작하지 않습니다.

커밋된 파라미터 포즈와 잠금은 런타임 보조 상태에 작업 공간별로 보관되며, `workspace.json`의 기존 작업 공간/캔버스 필드에 투영됩니다. 저장은 모든 작업 공간에 대해 캡처된 지속 값과 잠금을 사용하며, 일시적인 GUI 값과 평가된 프레임 캐시는 제외합니다. 질의, 미리보기 변경, 스냅샷 적용은 이전 포즈를 현재 파라미터 정의에 맞춰 정규화하지만, 읽기나 논리적 무작업에서 레코드나 히스토리를 다시 쓰지 않습니다. 작업 공간을 복제하면 복사된 지속 포즈를 등록합니다.

`workspace.json`의 선택적 `assetCatalog`는 `{version:1, assets:[ID...], workflow:[ID...]}`를 저장하며, 이는 에셋과 참조/등록 레코드의 커밋된 구성원입니다. 리소스는 기존 보조 디렉터리를 유지하며 Rig 저널에 들어가지 않습니다. 에셋 쓰기는 Rig 리비전이나 히스토리를 바꾸지 않고 지속되는 런타임 상태를 진행시킵니다. 저장은 캡처된 카탈로그에서 리소스를 복사하며, 이후 제출은 제외합니다. 카탈로그가 없는 이전 파일을 열면 히스토리를 다시 쓰지 않고 기존 불변 레코드로부터 구성원을 고정합니다. 새 프로젝트는 빈 카탈로그로 시작합니다. 열 때 구성원의 존재, 프로젝트 정체성, 참조 관계를 검증합니다. 검사와 합성은 캡처된 구성원을 사용하며, 커밋 전의 실패와 취소는 후보 파일을 게시하지 않습니다.

## 검증

열 때 버전(1 또는 2), 목록, 해시, 문서 노드 해시와 스키마, 페이로드 참조, 래스터, 히스토리 참조, HEAD를 검증합니다. 알 수 없는 문서 노드 종류나 더 새로운 스키마는 버리지 않고 거부합니다. 중복 항목, 밖으로 벗어나는 경로, 지원하지 않는 버전은 거부합니다. 압축 해제 한도는 항목 1,000,000개와 실제로 압축을 푼 64 GiB이며, ZIP에 선언된 크기가 아닙니다.

수동 편집은 참조를 보존하고 목록 해시를 업데이트해야 합니다. 일반 편집과 히스토리 작업은 UI를 사용하세요. 레거시 `.rgba.gz` 복구 리소스는 호환을 위한 읽기 경로로 남아 있을 뿐 주된 쓰기 형식이 아닙니다.

## 진입점

- PSD 가져오기: `Ctrl+Shift+O`, 프로젝트 열기: `Ctrl+O`.
- 저장 / 다른 이름으로 저장: `Ctrl+S` / `Ctrl+Shift+S`. 다른 이름으로 저장은 현재 프로젝트 옆에서 시작하며, 현재 프로젝트 파일도 기존 파일도 아닌 이름(`name-2`, `name-3`…)을 제안합니다. 대상이 이미 있으면 교체하기 전에 창 안에서 확인하며, 그것이 현재 프로젝트 파일이면 별도의 메시지를 표시합니다. 편집이 아직 적용되는 중에 요청한 저장이나 다른 이름으로 저장은 대기열에 들어가 상태 표시줄에 표시되고, 편집이 끝나면 실행됩니다. 나중에 누른 `Ctrl+S`가 대기 중인 다른 이름으로 저장을 일반 저장으로 바꾸지는 않습니다. 시스템 파일 대화 상자는 메인 창이 소유하며, 이미 하나가 열려 있을 때 다시 요청하면 열려 있는 것이 앞으로 나옵니다.
- MCP: `project_save`, `project_save_as`, `project_open`, 그리고 `history_checkpoint`, `history_list`, `history_checkout`. 다른 이름으로 저장과 열기는 UI 파일 선택 없이 절대 경로를 사용합니다. 변경 작업은 현재 `project_id`, 불투명한 `state`, 고유한 `request_id`를 함께 보냅니다. 같은 노드를 다시 열면 이전 state 토큰은 무효가 됩니다. 공개 요약은 내부 지속성 필드를 모두 노출하지는 않습니다. [MCP 계약](../agent/MCP_AUTHORING.md)을 참고하세요.

새로운 독립 Warp 생성은 안정적인 ID, 부모 및 메시 참조, 피팅 옵션을 가진 순서 있는 `authoringJournal` 항목을 사용합니다. 새 명령은 레거시 정적 Warp/구조 레코드를 덧붙이지 않습니다. 기존 레거시 레코드는 원래 재생 순서와 불변 히스토리 노드를 유지합니다.

모디파이어 인스턴스는 비용이 큰 평가의 완전한 상류 입력 정체성으로 `inputFingerprint`를 저장할 수 있습니다. 시뮬레이션 베이크와 이 정체성은 스택과 함께 `rig` 노드와 문서 리비전에 들어갑니다. 이 값은 편집 가능한 설정과 독립적입니다. 이 값이 없는 이전 인스턴스는 레거시 베이크 지문으로 계속 검증하며, 첫 후보 준비 때 완전한 정체성을 기록합니다.

모션 모디파이어에서 고정된 클립은 `captured_ranges`를 저장할 수 있습니다. 각 트랙을 고정할 때의 파라미터 최솟값, 최댓값, 반복 여부를 기록합니다. 이 필드가 있는 `clips` 노드는 스키마 7을 씁니다. 범위가 바뀌지 않으면 재구성해도 고정된 곡선 제어점을 그대로 유지하고, 범위를 실제로 편집했을 때만 곡선을 정리하고 기록된 범위를 갱신합니다. 이 필드가 없는 노드는 기존 스키마를 유지합니다.
