# 캔버스 렌더러

상태: 현재 구조는 10절의 통합 렌더러입니다. 창이 OpenGL을 사용하지 않으면(macOS, 소프트웨어 렌더링) 캔버스는 소프트웨어 경로를 사용합니다.
범위: 편집 캔버스(오브젝트 / 변형 / 편집 / 페인트 / 시뮬레이션)의 텍스처와 보조 레이어, 텍스처 작업 공간의 아틀라스 페이지, 미리보기 캔버스의 두 백엔드, 재생·추적 세션(11절).

렌더러는 `org.umamo.render`의 렌더링 코드를 사용하지 않고 모델 데이터만 읽습니다. `PuppetModel` / `Drawable` / `DrawableMesh`와 `RigCanvasSupport.evaluate`가 제공하는 변형 결과입니다. 변형은 CPU에서 계산하고 GPU는 텍스처 삼각형, 마스크, 셰이딩, 보조선만 처리합니다. GPU를 사용할 수 없으면 `SkiaRigPainter`가 소프트웨어로 그리며 첫 그리기 때만 아틀라스 페이지를 변환합니다. 따라서 GPU 캔버스는 이 변환 비용과 메모리를 부담하지 않습니다. 설정의 “그래픽”에서 “GPU 창, 소프트웨어 캔버스” 렌더링 경로는 편집 캔버스와 아틀라스 페이지에 함께 적용됩니다.

## 1–9. 초기 방식(대체됨)

원래 편집 캔버스는 CPU에서 픽셀별로 채웠습니다. Skia가 삼각형마다 4096 텍스처 페이지를 샘플링하고, Java2D가 보조 레이어를 전체 `BufferedImage`에 그렸습니다. 예제 `tml`(메시 24개, 정점 3467개, 4096² 페이지 하나, 캔버스 1600×1000)에서 CPU 변형은 0.3–0.7ms뿐이었지만 텍스처 그리기는 맞춤 배율에서 약 26ms, 4× 확대에서 약 82ms, Java2D 메시 와이어프레임은 12–20ms였습니다. 확대·축소, 드래그, 파라미터 변경 시 한 프레임이 100ms를 넘을 수 있었습니다.

이에 첫 GPU 렌더러는 독립 OpenGL 3.3 오프스크린 컨텍스트(숨긴 GLFW 창과 전용 스레드)를 사용했습니다. PBO로 비동기 읽기 반환한 Skia 이미지를 Compose에 전달하고, 새 프레임 도착 전에는 카메라에 따라 이전 프레임을 재투영했습니다. 이 경로는 텍스처·마스크·셰이딩(소프트웨어와 GPU가 `ArtworkDrawList` 공유), 모든 보조 레이어(`RigGuides`, Java2D와 피복도 비교 테스트), 페인트 필획의 부분 텍스처 업로드, 아틀라스 페이지를 차례로 GPU로 옮겼습니다. 대가는 두 번째 컨텍스트, 스레드 간 동기화, 1–2프레임 늦은 표시, 프레임마다 읽기 반환 복사였습니다. 10절의 통합 렌더러가 이를 제거했습니다. 독립 컨텍스트와 읽기 반환은 창 없는 상태에서 소프트웨어 결과와 비교하는 테스트 소스(`GlHost`)에만 남아 있습니다.

시작 로그는 창과 편집 캔버스의 렌더링 방식을 각각 기록합니다(예: `창 렌더링: SOFTWARE_FAST`, `편집 캔버스 렌더링: GPU(…)`). 창이 SOFTWARE이면 UI 전체를 CPU가 합성하므로 모든 패널과 애니메이션이 느려집니다. 이는 캔버스 렌더러와 무관하며 그래픽 드라이버나 Skiko 렌더링 백엔드 설정부터 확인해야 합니다.

## 10. 통합 렌더러(현재)

편집 캔버스, 아틀라스 페이지, 두 미리보기 백엔드는 렌더러 하나를 공유합니다. 모두 **창 자체의 Skia OpenGL 컨텍스트**에서 창을 그리는 스레드로 실행되며, Skia가 소유한 텍스처에 그리면 Compose가 같은 프레임에 표시합니다. 두 번째 컨텍스트도, 컨텍스트 간 공유·동기화도 없고, 어떤 픽셀도 GPU를 떠나지 않습니다.

### 10.1 컨텍스트와 턴

- 그래픽 설정(`render/GraphicsSettings.kt`, `AppSettings.graphics`에 영속화)은 `main`에서 창을 만들기 전 `GraphicsSettings.applyAtStartup`으로 적용합니다. Windows에서는 Skiko가 OpenGL을 사용하게 하고(기본은 Direct3D), “소프트웨어” 경로이면 `SOFTWARE`로 설정합니다. Linux의 Skiko는 원래 OpenGL을 사용합니다. 수직 동기화를 끄면 `skiko.vsync.enabled=false`로 설정합니다(Linux에서는 Skiko 교환 간격이 0이 되어 UI 스레드가 매 프레임 `glXSwapBuffers`에서 멈추지 않고, 타이머 `FrameLimiter`가 모니터 보고 주사율로 프레임을 제한합니다. 모니터가 없는 Xorg에서는 제한되지 않는 것을 실측했습니다. Windows에서는 제한하지 않습니다). Linux의 “드라이버 멀티스레드”와 GPU 선택은 OpenGL 라이브러리를 로드하기 전 환경 변수(`mesa_glthread`, `__GL_THREADED_OPTIMIZATIONS`)로 설정합니다. GPU 선택은 Linux에서 OpenGL 라이브러리 로드 전에 libc `setenv`(JNA)로 PRIME 분기 변수를 설정합니다(NVIDIA 독점 드라이버는 `__NV_PRIME_RENDER_OFFLOAD` / `__GLX_VENDOR_LIBRARY_NAME`, 나머지는 Mesa의 `DRI_PRIME=pci-…`. 실행 전에 지정한 변수는 덮어쓰지 않으며 GPU는 `/sys/class/drm`, 이름은 `lspci -mm`에서 읽습니다). Windows에서는 설치판 런처가 시스템의 프로그램별 그래픽 기본 설정(`HKCU\Software\Microsoft\DirectX\UserGpuPreferences`, “설정 > 디스플레이 > 그래픽”과 동일)을 기록합니다. macOS는 `skiko.metal.gpu.priority`를 설정합니다. 사용자가 명시한 `skiko.renderApi` / `SKIKO_RENDER_API`, `skiko.vsync.enabled`, `psd2live.msaa`가 우선합니다. 렌더링 API, GPU, 수직 동기화 끄기, 드라이버 멀티스레드는 시작 때만 적용되며 설정 페이지는 시작 시 값과 다르면 안내합니다. 나머지는 `GraphicsSettings.update`로 `GraphicsSettings.current`에 기록하여 렌더러가 다음 프레임부터 읽습니다. 창이 OpenGL이 아니면(macOS, 소프트웨어 렌더링) 캔버스는 소프트웨어 경로를 사용하고 미리보기에 이유를 보고합니다. Skiko는 `llvmpipe`와 `virgl`의 OpenGL을 거부하므로(GPU를 직접 전달하지 않은 WSL, 가상 머신 등) 이때 창은 소프트웨어 렌더링으로 전환합니다.
- `SkiaGpu.of(window)`는 창의 `SkiaLayer`에서 Skiko OpenGL 재그리기 객체의 컨텍스트 핸들과 이를 그리는 `DirectContext`를 읽어 `WindowGpu`를 얻습니다(Skiko가 공개하지 않아 리플렉션 사용). 창마다(메인 창, 떠 있는 도킹 창) 하나씩 있으며 자원은 공유하지 않습니다.
- `SkiaLayer.PropertyKind.Renderer`가 바뀌면 메인 창 GPU, 상태, 모든 캔버스의 컨텍스트 쿼리를 갱신합니다. 소프트웨어 대체와 OpenGL 재생성이 모두 반영되며 떠 있는 창도 감시합니다. 이전 `WindowGpu`는 GL 작업을 멈추고, 이전 프레임을 기다리던 코루틴은 깨어나 캔버스가 취소하거나 새 창 상태를 사용합니다.
- **현재 컨텍스트**(`GlBinding`): WGL에서 Skiko 재그리기 객체의 `context` 필드는 `HGLRC`입니다. GLX에서는 Skiko 네이티브 코드에서 `GLXContext`를 담은 변수의 주소이므로 그 값을 읽어야 `glXGetCurrentContext`와 비교할 수 있습니다(필드값만 비교하면 Linux에서 턴을 매 프레임 조용히 건너뛰어 캔버스에 배경과 Compose의 선택 윤곽만 남음). Skiko는 매 프레임 먼저 Compose를 기록하고(여기서 캔버스 그림), 창 컨텍스트를 현재로 설정한 뒤 재생합니다. 기록 중 현재 컨텍스트는 직전에 그린 창의 것이므로 떠 있는 창이 있으면 이 창과 다를 수 있습니다. 그래서 창 렌더링 델리게이트가 Compose 렌더링 전에 해당 창 컨텍스트를 현재로 만듭니다(WGL은 창 `HDC`, GLX는 Skiko 그리기 표면 잠금으로 X 디스플레이와 drawable을 얻으며 잠금은 재진입 가능). 델리게이트 래퍼는 메인 창을 캡처할 때와 턴의 현재 컨텍스트 검사 전에 설치합니다.
- **턴**(`WindowGpu.turn`): 해당 컨텍스트가 현재일 때만 실행합니다(`wglGetCurrentContext` / `glXGetCurrentContext` 비교). 시작과 끝에서 Skia가 남겼지만 그리는 쪽이 스스로 초기화하지 않는 상태(스텐실 클립 검사, 샘플러 객체, 픽셀 버퍼, 행 길이, 기본 정점 배열의 버퍼·속성 등)를 GL 기본값으로 복원하고, 끝에서 `DirectContext.resetGLAll()`로 Skia가 자체 상태를 다시 설정하게 합니다. 턴 시작 시 기본 상태를 복원하며 그리는 쪽이 사용하는 0–3번 텍스처 유닛만 지웁니다. 끝에서는 더 이상 복원하지 않습니다. Skia가 자신에게 필요한 상태를 재설정하고 다음 턴 시작 때 다시 복원하기 때문입니다. 턴 안에서는 `glGetError`를 호출하지 않습니다. 드라이버 스레드(NVIDIA threaded optimization, Mesa glthread)나 호스트 전달(WSL, 가상 머신)이 있으면 앞선 호출 전체를 드라이버가 처리할 때까지 기다려야 하기 때문입니다. 오류 검사가 필요한 곳(텍스처와 타깃 할당)은 호출 전에 오류를 비웁니다. 캔버스와 p2lrt 그리기 객체는 `DrawTarget`에서 대상 프레임버퍼를 받아 더 이상 `glGetInteger`로 조회하지 않습니다.
- 턴은 두 곳에서 실행합니다. 캔버스 그리기(`CanvasGpu.draw`, 미리보기 캔버스의 `drain`)와, 창 렌더링 델리게이트 바깥에서 프레임마다 Compose 그리기 전에 실행하는 게시 작업(`WindowGpu.post`, 로드·해제 및 캔버스가 유발하지 않는 작업용)입니다.
- 기본 VAO의 인덱스 버퍼, 속성, divisor는 호환 프로파일에서만 지웁니다. 코어 프로파일에서는 VAO와 배열 버퍼만 해제하고 그리기 객체가 자체 VAO를 바인딩하게 하여 VAO 0 수정의 `GL_INVALID_OPERATION`을 피합니다.
- `GpuTarget`: 뷰마다 줄어들지 않고 커지기만 하는 텍스처 하나(Skia가 `Image.adoptTextureFrom`, `TOP_LEFT`로 인계받음)와 깊이·스텐실 버퍼를 가집니다. 내용은 왼쪽 위, 첫 행은 위에 놓입니다. GL 관례대로 아래에서 위로 그리는 Cubism은 먼저 장면 버퍼에 그리고 `glBlitFramebuffer`로 수직 반전하여 복사합니다. 프레임마다 같은 텍스처를 덮어씁니다. 이전 프레임의 샘플링은 같은 컨텍스트에서 먼저 제출되었고 GPU가 순서대로 실행하므로 펜스가 필요 없습니다.

- **캔버스와 미리보기 안티앨리어싱**(“그래픽 → 안티앨리어싱 → 캔버스와 미리보기”, `CanvasAntialiasing`): `GpuTarget`은 `TargetQuality`에 따라 그리기 객체가 자체 버퍼에 먼저 그린 뒤 텍스처에 기록하게 합니다. MSAA는 다중 샘플 색 및 깊이·스텐실 렌더버퍼이고 `glBlitFramebuffer`로 같은 크기에 resolve합니다. SSAA 2×는 가로세로 두 배 버퍼이며 `GL_LINEAR`로 절반 축소합니다(정확히 2×2 박스 필터). 그리기 객체는 프레임버퍼 픽셀을 직접 주소 지정하는 곳(뷰포트, 클립, 혼합 레이어, 영역 복사)에서만 `DrawTarget.scale`을 곱합니다. 선폭과 점 반경은 화면 픽셀 기준을 유지하고 `u_viewport`도 바뀌지 않습니다. 다중 샘플에서는 마스크가 alpha to coverage로 스텐실을 씁니다(`MASK_COVERAGE` 셰이더: 완전 투명 텍셀만 버리고 텍셀 불투명도로 샘플 피복도 결정). 따라서 마스크 가장자리가 부드러워집니다. 혼합 레이어는 단일 샘플이며 여전히 반투명 임계값을 사용합니다. 특정 샘플 수나 배율에서 버퍼를 만들지 못하면(오류 또는 불완전) 그 값 이상은 다시 시도하지 않습니다(`RefusedQuality`). Cubism 미리보기는 위아래로 반전하여 기록하며 이 경로를 거치지 않습니다. `CanvasGpu`는 안티앨리어싱과 텍스처 필터를 캐시 키에 포함하여 변경 후 다시 그립니다.
- **텍스처 필터링**(`TextureFiltering`): 텍스처 페이지는 `PageTextures.upload`로 업로드하며 편집 캔버스와 p2lrt가 공유합니다. ARGB 정수를 `GL_BGRA` + `GL_UNSIGNED_INT_8_8_8_8_REV`로 그대로 올립니다(ARGB 정수의 메모리 바이트 순서이며 Windows·NVIDIA 드라이버의 텍스처 저장 순서이기도 함). 미리 곱한 알파 이미지는 픽셀별 재변환하지 않고 나머지만 미리 곱합니다. 축소 필터는 쌍선형, 삼선형, 삼선형+이방성(GL 4.6 / ARB / EXT의 `GL_TEXTURE_MAX_ANISOTROPY`, 드라이버 상한으로 제한)입니다. `FilteringFollower`는 설정 변경 후 다음 그리기에서 기존 텍스처를 재설정합니다.
- **창 안티앨리어싱, 수직 동기화와 캐시**: 창 안티앨리어싱은 Skia 피복도(0) 또는 MSAA 2×–16×(`MultisampledWindow`)입니다. “적응형” 수직 동기화는 Windows에만 있습니다(`AdaptiveVsync`: 프레임이 주사율을 못 따라가면 `DwmFlush` 일시 중단). Skiko Linux 재그리기 객체는 생성 시 교환 간격을 고정하므로 실행 중 전환하면 기존 대기 외에 타이머만 추가됩니다. “창 캐시”는 창 합성기입니다(`psd2live.compositor=false`면 여전히 강제 끔). “GPU 캐시”는 매 프레임 시작 시 `DirectContext.resourceCacheLimit`을 설정하며(`CacheBudget`), “자동”은 컨텍스트 생성 당시 예산으로 복원합니다.
- **성능 오버레이**(`PerformanceOverlay`, “그래픽 → 고급”): 창 렌더링 델리게이트는 프레임 끝마다 프레임 시작 간격과 UI 스레드 렌더링 시간을 기록합니다(`FrameStats`, 최근 120프레임, 250ms를 넘는 멈춤 제외). 켜면 Skia가 창 오른쪽 위에 직접 그리며 Compose를 거치지 않아 재구성·재그리기를 추가하지 않습니다. UI가 테마에 맞는 색을 전달합니다. UI 스레드 시간은 Compose 기록과 재생만 포함하고 뒤의 버퍼 교환·GPU 실행은 포함하지 않습니다.
- **품질 프리셋**(`QualityPreset`): 낮음, 중간, 높음, 매우 높음은 창 안티앨리어싱, 캔버스 안티앨리어싱, 텍스처 필터, GPU 캐시 네 항목을 각각 고정합니다. 기본값은 “높음”이며 다른 조합은 “사용자 지정”으로 표시합니다.

### 10.2 편집 캔버스와 아틀라스 페이지

`CanvasGpu.draw(window, viewId, key, scene)`는 캔버스 그리기 안에서 동기 실행합니다. 키가 같으면 GL을 건드리지 않고 이전 프레임을 그대로 반환합니다. 키가 바뀌었을 때만 장면을 만들고 턴 안에서 `GlCanvasRenderer.draw`로 뷰 텍스처에 그려 같은 프레임에 표시합니다. 큐, 읽기 반환, 재투영이 없어 이동·확대·축소가 즉시 정확한 프레임이 됩니다. `GlCanvasRenderer.render`(오프스크린 프레임버퍼 + 읽기 반환)는 창 없는 컨텍스트(테스트 소스의 `GlHost`)에서 소프트웨어 결과와 비교하는 테스트용으로만 남아 있습니다.

- 편집 캔버스: 카메라는 uniform 하나이므로 이동·확대·축소 시 데이터를 업로드하지 않습니다. 텍스처 페이지는 미리 곱한 알파와 mipmap을 사용합니다. 메시 그리기는 `.p2lrt` 미리보기와 같은 규칙입니다. 프래그먼트에서 먼저 straight color로 복원하고 곱셈 색을 곱한 뒤 스크린 색을 더합니다(색은 부모 디포머까지 합친 평가 결과 `DeformedGeometry.multiplyColor` / `screenColor`에서 가져옴). 마스크는 스텐실 버퍼에 쓰며 마스크 메시 텍셀 불투명도 ≥ 0.5일 때만 덮인 것으로 보고 역마스크는 같지 않음 판정을 사용합니다. 일반 + 덮기와 구형 가산·곱셈은 고정 파이프라인을 사용합니다. 다른 색·불투명도 혼합은 파츠를 마스크·호버 색과 함께 별도 레이어에 그리고 아래 화면을 복사한 뒤 같은 합성 셰이더(umamo `CompositeShaders`)로 합성하며 파츠 경계 상자 안 픽셀만 처리합니다. 격리 그룹(파츠의 오프스크린 합성)은 미리보기에만 표시합니다. 선택 / 호버 착색과 어둡게 하기는 기하를 바꾸지 않으며 소프트웨어·GPU 경로가 같은 `ArtworkDrawList`를 공유합니다. 보조 레이어(메시 와이어프레임, 디포머 격자·모서리 표시, 회전 포인터, 선택 상자, 변형 경로)는 `RigGuides`가 소프트웨어와 같은 기하를 제공하고, 이름·점 번호는 Compose 텍스트입니다. 페인트 시 초안 텍스처(`PaintScene`, 초안 래스터 크기)는 병합한 변경 사각형만 `glTexSubImage2D`로 부분 업로드하고 오버레이 뒤에 그립니다.
- 아틀라스 페이지(`AtlasScene`): 타일은 `TextureQuad`입니다(레이어별 래스터를 배열 인스턴스로 한 번 업로드하고 2배 이상 확대하면 텍셀 샘플링. 메시 기준 배치 타일은 먼저 셀을 스텐실에 기록). 히트맵은 `FillBatch`, 메시 와이어프레임은 `LineBatch`, 드래그·크기 조절 중인 타일은 맨 위에 그립니다. 윤곽, 선택, 꼭짓점, 상자 선택은 Compose가 그립니다. 텍스처 편집은 뷰모델의 직렬 큐 `queueTextureEdits`로 순서대로 커밋하고 대기 결과는 `TextureWorkspaceState.pending`으로 먼저 표시합니다.

### 10.3 미리보기 백엔드

미리보기 캔버스에는 두 백엔드가 있습니다. 왼쪽 도구 모음 맨 위의 “런타임”(Cubism SDK / p2lrt · 표준 / p2lrt · 확장) 또는 왼쪽 아래 상태 알약 메뉴에서 선택합니다(애플리케이션 설정이며 프로젝트에 저장하지 않음).

| 백엔드 | 모델 | 평가와 그리기 |
| --- | --- | --- |
| Cubism SDK | 내보낸 moc3(`CubismRuntimeBundle`) | 공식 Cubism 5-r.5 런타임(`CubismSdkPreviewSession`) |
| PSD2Live 런타임(p2lrt) | 내보낸 `.p2lrt`(`RigIrCompiler.compile(simulations = true)`) | `runtime/` 평가, `P2lrtGlRenderer` 그리기(`P2lrtPreviewSession`) |

- 둘 다 작업 공간 시계가 제공한 완전한 포즈만 렌더링하며 자체 모션이나 드래그를 실행하지 않습니다. p2lrt 확장(고급) 모드는 뷰별 모델에서 `p2l_set_advanced` 기능을 켭니다. 실시간 시뮬레이션·충돌은 재생과 무관하게 **물리 토글**로 제어합니다. 물리를 켜면 `p2l_update_stages(dt, P2L_STAGE_SIM)`으로 프레임 시간에 따라 실시간 시뮬레이션만 진행합니다(일시 정지 중에도 흔들림이 이어지고 프레임 펌프는 정지 대기에 들어가지 않음). 작업 공간에서 이미 합성한 물리 결과는 그대로 유지합니다. 물리를 끄면 시뮬레이션과 충돌을 끄고 베이크한 흔들림을 표시하며 스키닝·정밀 연결만 유지하고 `p2l_evaluate`로 평가합니다.
- p2lrt 백그라운드 컴파일은 공유 모델을 한 번 읽고 스키닝 가중치를 준비합니다. 뷰별 포즈·시뮬레이션 상태는 독립이고 확장을 켜면 피팅 결과를 재사용합니다. 렌더 작업 실행 중 들어온 새 요청과 컴파일 완료 알림은 후속 깨우기 한 번을 보존하므로 일시 정지된 뷰도 새 모델로 갱신합니다. 적용할 확장이 없거나 시뮬레이션 확장만 있는데 물리가 꺼져 있으면 상태 알약에 이유를 설명합니다.
- `PreviewSessions`는 둘을 같은 인터페이스 뒤에 둡니다. Cubism 라이브러리·모델 로드·그리기가 실패하면 자동으로 p2lrt로 바꾸고 로그를 기록합니다. 둘 다 사용할 수 없을 때만 편집 캔버스의 그리기 경로로 대체합니다. 코어 프로파일은 네이티브 라이브러리 로드 전에 거부하며, 기존 바인딩도 컨텍스트 교체 후 이전 모델 핸들을 사용할 수 없습니다.
- 네이티브 호출은 모두 `GpuExecutor` 작업입니다. 앱에서는 창 턴 안에서 실행하고(`PrimaryGpuExecutor`, `WindowGpu.post`), 테스트에서는 일반 스레드에서 실행합니다. 프레임 펌프가 프레임을 요청한 뒤 캔버스가 읽는 카운터를 늘립니다. 캔버스를 그릴 때 먼저 `drain`으로 이번 렌더 작업을 실행하고 해당 뷰 텍스처를 그리므로 방금 요청한 프레임이 표시됩니다.
- Cubism은 메인 창 컨텍스트에서 `Live2D_Init`으로 초기화하고 `Live2D_Draw`로 현재 프레임버퍼에 그립니다. 프레임워크의 셰이더 등 상태는 컨텍스트 하나에만 있으므로 떠 있는 창의 미리보기는 p2lrt로 그립니다. Cubism 렌더러는 클라이언트 메모리에서 정점을 읽어 호환 프로파일 컨텍스트가 필요합니다(Windows Skia는 전통적 호환 컨텍스트). 코어 프로파일에서는 오류를 보고하고 그리지 않습니다.
- 네이티브 브리지: 구형 `Live2D_CreateModelFromMemory`는 항상 브리지 자체의 숨긴 컨텍스트로 전환하여 모델이 잘못된 컨텍스트에 들어갔습니다. 다시 빌드한 브리지는 `Live2D_UsesCallerContext`를 내보내며 `Live2D_Init` 후 메모리 로드도 호출자 컨텍스트를 씁니다. 구형 브리지는 이 모드에서 임시 파일 로드(`Live2D_CreateModel`)로 바꾸고 재로드 때마다 완전히 다시 구성합니다.
- p2lrt 컴파일은 독립 스레드에서 수행합니다. 메시·텍스처 페이지는 컨텍스트별로 업로드하고(`GpuResources.service`) 뷰별로 런타임 인스턴스를 둡니다.

### 10.4 프레임률

미리보기 프레임 펌프는 디스플레이 갱신마다(`WindowGpu.awaitFrame`) 한 프레임을 요청합니다. 프레임률 상한은 앱 설정(모니터 따르기 / 30 / 60 / 120, 기본은 모니터 따르기이며 미리보기 메뉴와 “설정 → 그래픽”이 같은 항목을 변경)입니다. 프로젝트 물리 프레임률과는 무관하며 물리는 고정 스텝 사이를 보간합니다. 상한이 있으면 `awaitFrame` 만료 반 주사 주기 전에야 창 프레임을 요청하므로 미리보기만 건너뛰는 것이 아니라 창 자체도 덜 그립니다. 비활성 창은 “백그라운드 프레임률”과 비교해 더 낮은 값을 씁니다. 여러 미리보기가 동시에 보여도 각각 30FPS로 제한하지 않습니다.

높은 주사율에서는 프레임 시간 대부분이 CPU에서 쓰입니다(`PreviewFpsTool`, 240Hz, 편집 작업 공간). Skia의 전체 창 기록→GPU 작업 변환이 약 2ms, 제출이 약 1.8ms, GPU 실행은 약 0.5ms뿐이며 미리보기 런타임·Cubism 평가는 UI 스레드 시간의 2% 미만입니다. 변환의 상당 부분은 안티앨리어싱 경로·둥근 모서리·타원의 피복도를 CPU에서 계산하는 데 쓰이므로 GPU 다중 샘플링으로 줄일 수 있습니다. Skiko 창 표면은 단일 샘플이어서 `MultisampledWindow`가 Compose의 매 프레임 기록을 창 크기 MSAA 텍스처로 재생합니다(기본 4×, “그래픽 → 안티앨리어싱 → 창”에서 샘플 수를 읽고 다음 프레임부터 적용. `psd2live.msaa`가 설정을 덮어쓰며 0은 Skia 자체 피복도 안티앨리어싱). 창은 이 텍스처 하나만 그립니다. 특정 샘플 수에서 타깃을 만들지 못하면 그 이상은 다시 시도하지 않습니다. 반드시 먼저 기록하고 재생해야 합니다. Compose를 그 텍스처에 바로 그리면 레이어(Skiko 렌더 노드) 제출이 오히려 몇 배 느려집니다. 8×는 4×보다 느립니다. 편집 작업 공간 실측(수직 동기화 대기 없음)은 프레임당 약 7.5ms에서 6.1ms로 줄었습니다.

고주사율 예산(`PreviewFpsTool`, RTX 4080 노트북, 240Hz): Windows Skiko는 프레임마다 UI 스레드에서 Compose(재구성, 레이아웃, 그리기 기록), Skia의 창 기록 GPU 재생, 버퍼 교환과 `glFinish`를 순서대로 수행하고 `DwmFlush`로 다음 갱신을 기다립니다. 프레임이 4.17ms를 넘으면 두 번 갱신을 기다려 120FPS로 떨어집니다. Compose Desktop은 어떤 변화에도 창 전체를 다시 그리며, 패널이 그대로여도 모든 그리기를 재생합니다. 편집 작업 공간에서는 이것만 매 프레임 약 5–6ms입니다. 따라서 미리보기 프레임은 Compose를 거치지 않고 창에서 합성합니다.

- **창 합성기**(`WindowCompositor`, `WindowGpu` 렌더링 델리게이트 안에 설치): 매 프레임 먼저 미리보기 프레임 펌프를 깨우고 GPU 작업(미리보기 텍스처 렌더링)을 수행한 뒤, Compose를 정상 실행하여 비용이 작은 Picture에 기록합니다. 장면의 `SnapshotInvalidationTracker`가 재그리기·재배치 요청을 보고했거나(콜백을 카운터로 감쌈) 창 크기가 바뀌었을 때만 기록을 캐시 텍스처로 재생합니다. 캐시 텍스처는 앞의 창 타깃처럼 다중 샘플(`psd2live.msaa`)이며 합성하지 않을 때도 창은 `MultisampledWindow`를 사용합니다. 화면은 각 `CompositedView`(미리보기 배경, 캔버스 테두리, 최신 프레임) 위에 캐시 텍스처를 얹습니다. Compose 내부는 리플렉션으로 얻으며 실패하거나 창 컨텍스트가 현재가 아니면 기존 방식으로 그립니다(`WindowGpu.composited`가 false). `-Dpsd2live.compositor=false`로 끕니다.
- **미리보기 캔버스에 구멍 내기**: 합성 시 네이티브 프레임을 사용하는 미리보기 캔버스는 `CompositedView`를 등록하고 `BlendMode.Clear`로 자신의 영역을 비웁니다. 이후 그리는 도구 모음·메뉴는 캐시 화면에 남아 미리보기 위에 위치합니다. 캔버스 그리기와 합성은 프레임별 상태를 읽지 않습니다. 프레임 펌프는 구멍을 낼 때 `previewTick`을 늘리지 않고 합성은 백엔드·확장 모드처럼 드물게 바뀌는 값만 읽습니다.
- MSAA를 끄거나 할당에 실패하면 창 캐시와 편집 캔버스 합성 레이어 모두 0샘플 텍스처로 바꿉니다. 내용 무효화 때만 다시 그리는 캐시 규칙은 유지합니다. `GpuCompatibilityTool`은 두 GL 프로파일의 상태 정리, MSAA가 없을 때 캐시 적중과 무효화 뒤 픽셀, 메인·떠 있는 창의 백엔드 교체를 확인합니다.
- **프레임 펌프**는 Compose 프레임 시계 대신 `WindowGpu.awaitFrame`을 기다립니다(프레임 시계에 대기자가 있으면 Compose가 매 프레임 다시 그림). `Dispatchers.Main.immediate`에서 실행하며 프레임 시작에 인라인으로 미리보기 프레임을 요청합니다.
- 재생 중 문서 상태에 쓰는 미리보기 포즈 빈도는 0.5초마다 한 번으로 낮춥니다. 쓸 때마다 상태를 읽는 패널이 재구성되고 창 전체를 다시 그리기 때문입니다. 패널은 `livePoseShown`을 읽습니다(최대 약 60Hz). 파라미터 행은 트랙·2D 패널 그리기, 수치 텍스트, 초기화 버튼 상태에서만 실시간 값을 읽으며 수치 입력 상자는 포커스 전까지 텍스트입니다. 포즈를 표시하지 않는 패널(계층 트리, 뼈대, 히스토리, 로그, 모델 프리셋, 레이어 표)은 포즈(미리보기 또는 작성자 포즈)만 바뀌면 기존 상태 인스턴스를 유지합니다(`withoutPose`: 필드별로 새 포즈를 넣어 비교하고 동일 하위 객체는 참조로 단락 평가하며 전체 복사를 하지 않음). 도킹 트리 자체(분할, 탭, 패널 헤더)도 포즈 없는 상태만 받고, 각 모듈은 자체 구성 범위에서 실시간 상태를 읽으므로 포즈 변경 시 캔버스·파라미터처럼 포즈를 읽는 모듈만 재구성합니다.
- 파라미터 슬라이더 드래그는 포인터 샘플마다 작성자 포즈를 씁니다. 파라미터 행은 `ParameterRowState`로 작성자 포즈, 잠금 집합, 편집 가능 상태를 각각 구독하여 전체 상태를 따라 재구성하지 않습니다. 작성자 포즈는 영속 콘텐츠지만 드래그 중에는 샘플마다 복구 체크포인트에 알리지 않고 놓을 때 한 번 알립니다(매번 전체 문서 인코딩과 체크포인트 다시 쓰기가 필요하기 때문).
- **합성기가 편집 캔버스를 그림**(`CompositedCanvas`): 합성 시 GPU 편집 캔버스의 아트 레이어와 편집기 오버레이(메시 점·선, 가이드, 핸들)가 각각 `CompositedView`를 등록합니다. 아트 레이어는 `BlendMode.Clear`로 구멍을 내고 오버레이는 지우지 않습니다. 둘의 Compose 그리기는 구멍 내기·등록만 수행하며, 기존 그리기 코드는 합성 단계에서 `CanvasDrawScope`로 Skia 캔버스에 그립니다. 각각 Picture로 기록하고 읽은 스냅샷 상태는 `SnapshotStateObserver`가 추적합니다. 상태가 바뀌면 해당 뷰만 만료시키고 창 재그리기를 요청하며 Compose 장면은 무효화하지 않습니다. 재구성된 그리기 함수는 `rememberUpdatedState`로 읽고 역시 뷰만 만료시킵니다. 같은 캔버스의 두 뷰는 하나의 합성 레이어(`CompositedView.layer`)에 속하여 캐시 화면과 같은 다중 샘플 텍스처에 함께 그리며, 둘 중 하나가 만료되었을 때만 다시 그립니다. 따라서 형상 안티앨리어싱·혼합(가중치 칠하기의 DST 혼합)은 Compose에서 그릴 때와 같고 바뀌지 않은 프레임은 텍스처 하나만 붙입니다. 도구 모음, 메뉴, 뼈대 편집 레이어 등은 캐시 화면에 남아 캔버스 위에 놓입니다. 합성기를 사용할 수 없으면 기존 방식으로 그립니다.
- 포즈 변경 때 여전히 재구성하는 UI도 위치 콜백이 있는 노드를 더 이상 바꾸지 않습니다. modifier 노드 갱신은 전체 창 재배치를 요청하여 전체 재생을 유발합니다. 상태 표시줄·작업 공간 탭 바는 포즈 없는 상태(`withoutPose`)만 받고 `tutorialTarget` 위치 콜백은 대상별로 기억합니다.
- `GridIcon`은 비트맵에 한 번 그리고 이후 매 프레임 텍스처 한 번으로 표시하여 여러 안티앨리어싱 경로를 대신합니다.

실측: 편집 작업 공간은 갱신 대기 없이 프레임당 약 1.8ms(이전 9.5ms), 갱신 대기 시 약 215FPS, 미리보기 작업 공간은 약 230FPS였습니다. 애니메이션·물리 작업 공간의 파라미터 패널과 진자 캔버스는 재생 중 계속 변하여 매번 전체를 다시 그리므로 약 100–170FPS입니다. 더 높이려면 패널별 캐시가 필요합니다. 일시 정지 상태의 합성과 기존 방식 화면은 픽셀별로 같았습니다(`PSD2LIVE_CAPTURE=1` 비교). 편집 작업 공간에서 240Hz로 슬라이더 드래그를 샘플링하면(`PSD2LIVE_SCRUB=EDIT`) 약 54FPS, 샘플당 UI 스레드 0.5ms였습니다. 앞의 구독·지연 알림과 네이티브 평가 세션의 인스턴스별 캐시를 적용한 뒤 약 98FPS, 0.13ms, 도킹 트리가 포즈를 따라 재구성하지 않게 한 뒤 약 107FPS였습니다(갱신 대기 없이 약 127FPS, 프레임당 약 7.9ms: 구성 약 3.2ms, 나머지는 Skia의 전체 창 기록 재생과 버퍼 교환). 당시 편집 캔버스는 Compose가 그렸으므로 포즈가 바뀔 때마다 창 합성기가 전체를 재생했습니다. 다른 편집 캔버스 상호작용도 같았습니다(`PSD2LIVE_GESTURE`, 갱신 대기 없음). 234점 얼굴 메시 호버는 약 150FPS이며 UI 스레드 절반 가까이가 Skia의 전체 창 기록 재생·제출이었습니다. Deform에서 모든 점을 드래그하면 약 91FPS, 전체 창 재생 약 35%였습니다. 재생은 이 제약을 받지 않았습니다. 애니메이션·물리 작업 공간의 미리보기 재생(P2LRT, 갱신 대기 없음)은 각각 약 500·300FPS였습니다.

편집 캔버스를 합성기로 옮기고 상태 표시줄·탭 바가 포즈를 따라 재구성하지 않게 한 뒤(같은 기기, 같은 날, 갱신 대기 없이 5초 비교): 슬라이더 드래그 약 114 → 393FPS, Compose 기록 재생은 프레임마다 한 번에서 총 2번으로 감소했습니다. 호버는 약 90 → 469FPS, 재생 517 → 87회, Deform 전체 점 드래그는 약 99 → 217FPS, 재생 577 → 96회였습니다(남은 재생은 제스처 시작 시 모드·선택 변경). Deform의 남은 시간은 주로 편집기 `move`와 오버레이 다시 그리기입니다. 일시 정지 화면을 비합성 화면과 비교하면 메시·아트 레이어는 일부 픽셀만 1–2단계 차이가 있고, 반투명 도구 모음 가장자리는 캐시에 먼저 그린 뒤 캔버스에 얹으므로 반올림 차이가 최대 약 18단계였습니다(`PSD2LIVE_CAPTURE=1`, `PSD2LIVE_SCRUB_HZ=0.001`로 샘플을 한 번만 보내 결정적인 정지 화면 확보).

### 10.5 p2lrt 그리기 규칙

`p2l_runtime.h`의 “Drawing” 규칙을 따릅니다. `p2l_render_commands` 순서로 뒤에서 앞으로 그리고, 텍스처는 미리 곱한 알파로 업로드하고 mipmap을 만듭니다. 프래그먼트에서 straight color로 복원한 다음 곱셈 색·스크린 색을 적용하고 메시 불투명도에 따라 미리 곱한 색을 출력합니다. 메시 마스크는 스텐실에 기록하며(텍셀 불투명도 ≥ 0.5만 피복으로 인정, 역마스크는 같지 않음), 메시가 요청하면 뒷면을 제거합니다. 카메라는 Cubism의 구도 파라미터(캔버스 높이가 짧은 변 × `scale`, 오프셋은 클립 공간 단위)를 사용하므로 두 백엔드의 구도가 일치합니다.

- 혼합: 일반 + 덮기와 Cubism 가산·곱셈(불투명도 혼합 방식 무관)은 고정 파이프라인의 미리 곱한 알파 조합을 사용합니다. 나머지 색 혼합(0–17)·불투명도 혼합(0–4) 조합은 메시를 비운 별도 레이어에 그린 뒤 편집기 Cubism 경로의 합성 셰이더(umamo `CompositeShaders`, `BlendMath.compositeReference` 참조)로 타깃 스냅샷에 합성하며 기본 모드로 대체하지 않습니다.
- 격리 그룹(`p2l_render_commands`의 그룹 열기 / 닫기 명령): 그룹 명령을 중첩 깊이별로 재사용하는 레이어(각각 스텐실 포함)에 그리고, 그룹 혼합 모드, `p2l_part_composite`의 불투명도·곱셈 / 스크린 색, `p2l_part_masks`의 마스크 피복도(마스크 메시 텍셀 불투명도의 최댓값)에 따라 이전 레이어로 합성합니다. 일반 + 덮기, 불투명도 1, 중립 색, 마스크 없음, 내부 모두 일반 + 덮기인 그룹은 원래 위치에 바로 그립니다(동일 결과로 레이어 생략). 레이어·스냅샷·피복 텍스처는 프레임 크기에 따라 커지기만 하고 줄지 않습니다.
- `P2lrtGlRendererTest`는 OpenGL 3.3 컨텍스트에서 픽셀을 읽어 `compositeReference`와 18 × 5 조합 및 격리 그룹(색, 마스크·역마스크, 중첩, 그룹 내 마스크 메시와 확장 혼합 메시)을 하나씩 비교합니다.

### 10.6 편집 캔버스 소프트웨어 경로의 마스크

`SkiaRigPainter`는 더 이상 마스크 메시의 모든 삼각형을 경로로 합쳐 자르지 않습니다. 마스크를 적용할 파츠를 삼각형 경계 상자 크기 레이어에 그리고, 마스크 메시 합집합을 `DST_IN` 레이어로 합성합니다. 마스크 메시에는 텍셀 불투명도 임계값(≥ 0.5, 색상표 필터)을 적용한 뒤 `DST_IN` 레이어로 합성하며 역마스크는 `DST_OUT`입니다. GPU 경로의 스텐실 버퍼와 같은 효과입니다. 곱셈 / 스크린 색은 straight color에 적용하는 색 행렬입니다. 일반 + 덮기 외 혼합은 파츠를 레이어에 그린 후 SkSL 블렌더(`skslCompositeBlender`, GLSL 합성 셰이더와 동일 수식 공유)로 아래에 합성합니다. `CompositeBlenderTest`는 18 × 5 조합을 `compositeReference`와 비교합니다. Java2D 그리기(MCP 뷰)도 같습니다. 마스크·색·다른 혼합이 있는 파츠를 레이어에 그리고 `CubismComposite`가 픽셀마다 `compositeReference`를 호출해 합성합니다.

### 10.7 검증

`PreviewWindowTool`은 실제 창을 엽니다. 편집 캔버스와 두 미리보기 백엔드가 모두 창의 Skia 컨텍스트에서 프레임을 만들고 GPU에서 읽어 확인합니다(뷰 텍스처만 읽고 화면 캡처는 하지 않음). RTX 4080 노트북에서 두 백엔드 모두 재생 시 100FPS를 넘었고 프레임률 잠금은 없습니다. 도구에는 워치독이 있어 창이 2분간 멈추면 스레드 덤프를 남기고 종료합니다.

### 10.8 캔버스 보조: 격자, 가이드, 어니언 스킨

편집 캔버스의 그리기 보조는 편집할 때만 표시하며 리그·히스토리·내보내기에 들어가지 않습니다. 순수 계산은 `ui/CanvasAids.kt`(`CanvasAidsTest`)에 있습니다.

- **설정**: 토글과 파라미터는 캔버스 뷰 옵션의 `TabViewOptions.aids`(`CanvasAidOptions`)이며 작업 공간 표시 상태에 저장합니다. 기본값과 다른 필드만 기록하여 사용하지 않은 캔버스의 바이트는 바꾸지 않습니다. 색은 테마 의미(`CanvasAidColor`)로 저장하고 그릴 때 `ToolColors`를 사용하므로 테마를 바꿔도 잘 보입니다. 격자·가이드 토글과 설정은 캔버스 오른쪽 아래 표시 바에, 어니언 스킨 토글과 설정은 애니메이션 편집기 도구 모음에, 무작위 포즈는 파라미터 패널 도구 모음에 있습니다. 뒤의 두 기능은 `PSD2LiveViewModel.aidCanvas`에 적용합니다(현재 캔버스가 편집 캔버스이면 그것, 아니면 표시된 첫 편집 캔버스).
- **표시 바와 “보기 ▾”**: “보기 ▾”(`CanvasViewMenuItems`)는 모든 표시 토글을 나열합니다. 표시 바에는 사용자가 고정한 항목만 놓고(`CanvasRailEntry`, `AppSettings.canvasRail`에 전역 저장, 메뉴 오른쪽 핀으로 추가·제거), 캔버스에 표시할 내용이 있을 때만 나타납니다(`CanvasViewContent.shows`: Warp / 회전 디포머 / 변형 경로 / 뼈대 / 메시 / 참조 이미지가 없으면 해당 항목 숨김). 두 곳이 `canvasViewToggle`의 라벨·아이콘·전환을 공유합니다.
- **가이드**는 프로젝트 데이터입니다. `WorkspaceAuxiliaryData.canvasGuides`는 파라미터 스냅샷과 같은 런타임 보조 CAS(`WorkspaceAuxiliaryEdit.SetCanvasGuides`)를 거치며 모든 편집 캔버스가 공유합니다. 드래그는 `CanvasGuideDrag`만 바꾸고(캔버스 그리기·포인터 처리에서 읽음) 놓을 때 한 번 저장하며, 눈금자로 되돌려 드래그하면 삭제합니다. 보조 쓰기는 새 상태 토큰을 발행하므로 편집·포즈 커밋·시뮬레이션 베이크·편집기 제스처 중 새 가이드는 먼저 VM의 저장 대기 초안으로 표시하고(`canvasGuides(state)`) 유휴 상태에서 커밋합니다. 내용이 같은 보조 편집은 원래 상태를 유지합니다(`WorkspaceHost.editSavedProjectData`). 캔버스의 가이드는 선택 계열 도구와 변환 도구에서 Shift/Alt를 누르지 않고 포인터가 편집기 핸들 위에 없을 때만 잡습니다. 눈금자에서는 항상 새 선을 끌어낼 수 있습니다.
- **격자, 가이드, 눈금자**는 별도 합성 뷰 `$gpuKey/aids`(`order = 3`, 오버레이·참조 이미지 위)에 그립니다. 그리기는 기억된 람다이며 `rememberUpdatedState`로 옵션·가이드·색을 읽습니다. 카메라·옵션·가이드만 읽으므로 재구성, 포즈 변경, 호버는 재기록을 유발하지 않습니다. 격자 간격은 배율에 따라 구분 가능한 단계(`CanvasGrid.step`, 화면 간격은 dp)를 고르고 스냅도 같은 단계(`CanvasGrid.nearest`)를 사용합니다. 스냅은 포인터가 아니라 드래그하는 점에 적용합니다. 캔버스가 `CanvasSnap`을 `CanvasEditor.snapScreenPoint`로 감싸고, 편집기는 첫 이동 때 누른 위치에 가장 가까운 드래그 점을 기준점으로 정해 `snap(기준점 + 변위) - 기준점`으로 변위를 보정합니다. 히트 테스트와 호버는 항상 원래 포인터를 사용합니다. 스냅은 메시 점·디포머 점의 평행 이동 드래그(핸들을 잡지 않았거나 상자 본체를 잡은 경우)에만 적용합니다. 변환 상자의 회전·크기 핸들, 뼈대 포즈, 앵커, 배치 핸들, 베지어 앵커·핸들, 새 디포머·경로 점 클릭은 의도적으로 스냅하지 않습니다. 페인트·변형 브러시도 스냅하지 않습니다.
- **어니언 스킨** 포즈는 구성 중 결정하지만 평가 자체는 구성에서 하지 않습니다. 모션이 열려 있으면 재생 헤드 전후의 프레임 간격 시각을 사용하고(`OnionSkin.frameGhosts` + `MotionClips.sampleAll`), 아니면 최근 설정한 파라미터의 현재값 양쪽 키를 사용합니다(`OnionSkin.keyGhosts`, 선택 객체에 키가 있으면 해당 키 사용). 유령 하나마다 `Dispatchers.Default`에서 `RigCanvasSupport.evaluate`로 커밋된 미리보기 모델의 기하를 평가합니다(`produceState`, 새 결과 전까지 이전 프레임 유지). 드래그 제스처·파라미터 슬라이더 드래그 중에는 기존 위치에 고정하고 재생 중에는 숨깁니다. 기하와 평가에 사용한 모델을 함께 각자의 GPU 뷰(`$gpuKey#onion<i>`)에 그리고, 레이어 전체 불투명도와 `SRC_ATOP` 착색으로 아트 레이어 위에 얹습니다. 키가 같으면 다시 그리지 않습니다. 소프트웨어 경로도 같은 레이어 불투명도·색 필터를 사용합니다. 끄면 평가하지도 뷰를 점유하지도 않습니다.

## 11. 재생과 추적 세션

캔버스의 재생·마우스 추적 버튼과 애니메이션 패널은 애플리케이션 계층의 재생 세션(`WorkspacePlaybackSessions`)을 공유합니다. 프로세스 임시 세션이며 프로젝트나 히스토리에 들어가지 않습니다.

- 모션이 열려 있으면 캔버스와 애니메이션 패널이 함께 그 모션을 재생 / 일시 정지하며, 열려 있지 않으면 대기를 제어합니다. 모션 자연 종료, 교차 일시 정지·재개는 로컬 토글만 바꾸지 않고 세션이 기록합니다.
- 마우스 이벤트는 포인터 좌표만 갱신하고 다음 시계 프레임에 평가합니다. 작성자 포즈 커밋 후에도 추적 상태와 일시 정지된 재생 헤드를 유지합니다. 시계 프레임은 물리 합성 뒤에 게시하며, 늦게 도착한 프레임이 제어 명령 이후 재생 헤드나 포즈를 덮어쓸 수 없습니다. 프로젝트를 다시 열면 이전 세션 프레임을 거부합니다.
- 두 미리보기 백엔드 모두 세션이 제공한 완전한 포즈를 소비하고 자체 모션·드래그·물리 시계를 실행하지 않습니다(§10.3). 소프트웨어 미리보기도 같은 결과를 사용합니다.
- 마우스 추적은 대기·모션과 독립된 합성 단계입니다. 기본은 즉시 매핑이며 미리보기 도구 모음의 “부드러운 추적과 몸 Y”를 켜면 직렬 지수 응답(`PreviewAnimationClock`)으로 바꿉니다. 머리 응답률 18/s, 몸 10/s이며 고정 목표의 90%에 약 150ms / 350ms에 도달하여 몸에 짧은 지연이 남습니다. 경과 시간으로 해석적으로 갱신하므로 프레임률이 달라도 같은 응답이며 시간 스텝 0은 원래 포즈를 유지합니다. 이 토글은 작업 공간 표시 상태에 저장하고 이전 프로젝트의 누락값은 끔입니다. 알고리즘 전환 시 포인터 위치를 유지하며 추적을 끄면 즉시 따라가기를 멈춥니다.
- 편집한 프리셋 모션은 패널의 preset ID를 계속 사용합니다. 제어 명령은 이전 렌더 프레임을 지워 재생 헤드 조정 뒤 이전 포즈가 남지 않게 합니다.
